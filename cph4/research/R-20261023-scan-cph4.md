## 四、长上下文 / 记忆压缩 · 多 agent 生产案例

## 五、与现行做法的冲突（我们怎么做 → 外部怎么说 → 后果）
1. **轮询 vs 事件**：我方 5 分钟 cron 轮询 → A2A 把 push notification / subscribe / streaming 列为一等更新机制，polling 明写「高延迟、多余请求、仅适合简单集成」→ 后果：跨机任务 p50 延误约 150s，空轮询持续烧额度，长任务（>5min）天然接不住。
2. **16k 上下文**：我方按 16k 跑 CLI → 官方口径是任何窗口都有污染，靠 compaction + 清工具结果 + 子 agent 隔离扩产能，而非缩小窗口 → 后果：长文档/多轮任务提前截断，失败表现为「忘前文」，不报错、难归因。
3. **注册表形态**：我方「文件系统即注册表 + 总册」→ Agent Skills 标准已把 name/description/license 写成硬约束，ClawHub 侧已上签名清单与版本历史 → 后果：无 frontmatter 校验=技能触发词漂移；无 license/签名字段=引第三方技能时无出处、无法审计。
