# Token / 上下文优化工具池 v1（2026-11-06 · GitHub 寻源结论）

> 用途：集团各线「少烧 token 不掉质量」的现成轮子清单 + 哪条线用哪个 + 质量护栏。
> 本文是资产（工具清单），不是机制；不新增流程、不新增巡检卡。落地一律接各线现有产线。
> 硬前提：**压缩比与质量必须同批 A/B 实测**，只认实测，不认 README 数字。

## 一、四层结构（从上到下越靠前越安全）

1. **少读层**（不压缩内容，只减少喂进去的量）— 质量零风险，优先做
2. **瘦身层**（清掉死的系统提示/技能/记忆，可逆）— 质量零风险
3. **折叠层**（工具输出、日志、历史摘要化）— 低风险，需保留可回溯原文
4. **算法压缩层**（改写字面/抽取压缩，模型看到的是压缩稿）— 中风险，只许用在非精确文本

## 三、质量护栏（不这么做就等于降质）

1. **黄金集 A/B**：用现有本地模型雷达的黄金集思路（考题自带证据），同一批真实任务，压缩前/后各跑一遍，按命中与人工判分对比。
2. **白名单免压**：台账、订单、法律/合规条款、数值与回测数据、代码原文、提示词规格、正典文件一律不压，只许索引化。
3. **压缩比上限**：首版一律 ≤40%，超过要先证质量不降。
4. **可回溯**：压缩件必须保留原文指针（文件+行号或哈希），模型要细节时能取回。
5. **算净收益**：省 token 但作废 prompt cache 的，可能净亏——用 distil 口径核一次。
6. **判负就关**：任一线实测质量下降，该线立即关压缩，只留少读层。

## 四、各线怎么用

1. **主控 / 治理线**：只上少读 + 瘦身。orders/台账/记忆禁压；claude-slim 先审一遍启动开销。
2. **BigStream（MV/漫剧/短剧）**：提示词包、分镜表、剧本禁算法压缩（细节即质量）；用模板+正典引用去重，工具输出折叠即可。
3. **BigMoney（量化）**：日志可折叠，价格/成交/回测数字禁压；建议 splitrail 先做成本基线。
4. **游戏线（吸嘟嘟/小游戏/Unity）**：代码检索走 sdl-mcp 或 repomix + repo map；Unity 资产查询已有 Unity Insight VFS，属同类方案，不重复引入。
5. **文案/运营/B站回复线**：可以上 leanctx 一类，但必须过既有「人味机械闸」再发。
6. **客服/内部问答**：算法压缩收益最大，也是唯一可以放开到 50%+ 的线，前提是答案能回指原文。

## 四·五、实测结果（2026-11-06 · 本机真跑·cl100k_base 统一计量）

台架：`.codely-cli/tmp/toktest/`（corpus.py 取语料 / code_quality.py 量代码保真 / measure.py 量文档保真 / report.json 原始数）
语料：本仓真实文件——orders.md 尾段、TOOLBOX 规格、`Tools/fleet/model_radar.py`、`LOCAL-MODEL-POLICY.json`、`Tools/fleet` 全 149 个 .py

### 1. 代码上下文（149 文件，原始 388,545 tokens）
| 方案 | 输出 tokens | 省 | 文件名 | 符号名 | 数值常量 | 字符串字面量 |
|---|---|---|---|---|---|---|
| repomix 原样打包 | 403,768 | -3.9% | 100% | 100% | 100% | 100% |
| **repomix --compress** | **214,213** | **44.9%** | 100% | **100%** | 87% | **32%** |
| contextshield --skeleton | 54,931 | 85.9% | 100% | 97% | 66% | 12% |

结论：**repomix --compress 是代码面唯一可用的**——省 45% 且符号零丢失。但它吃掉 68% 的字符串字面量（报错文案、提示词、键名），所以只适合「读懂结构」，改代码时不能用压缩包。
contextshield 省 86% 但常量只剩 66%、字面量只剩 12%，只适合「看个大概」。

### 2. 中文文档（4 份真实语料，含台账/规格/代码/JSON）
| 方案 | 省 | 事实原子 | 稀有事实 | 否定词 | 路径 |
|---|---|---|---|---|---|
| 朴素截断 40% | 37.5-43.2% | 40.7-91.2% | 30.5-85.2% | 83-100% | 0-100% |
| LLMLingua-2 @0.4 | 44.2-50.2% | 71.9-92.2% | 64.8-75.9% | **0-72%** | **0-36%** |

两个方案失败的方式不同，这点比总分更重要：
- **截断**是丢整段——保留的句子完整（否定词 83-100%），但尾部整节消失（规格文件原子只剩 40.7%）
- **LLMLingua** 是丢句内词——覆盖均匀（规格文件原子 71.9%），但把否定词打到 31%、路径打到 0%，句子结构被掏空

结论：**LLMLingua-2 在中文上不能用**。实测三处硬伤：
- 中文逐字丢弃约 70%，并在汉字间插空格（rate 0.6 只省 11.6%，rate 0.8 反而膨胀 19.7%）
- 文件路径保留率 0-36%、否定词（禁/不得/一律）只剩 0-72%——正是规则类文本最不能丢的东西
- 规格/台账这类「每句都是约束」的文本，两者都保不住路径与否定 → 只能不压

### 3. 英文对照
LLMLingua-2 压英文 README：省 53.1%，文字连贯可读。→ 工具本身没问题，是中文不适用。

### 4. 启动上下文开销（最大单笔）
- 项目 CODELY.md = 10,715 tokens
- 全局 CODELY.md = 17,641 tokens
- 合计 **28,356 tokens** 在每会话开头注入

结论：瘦身（claude-slim 那一类）比任何压缩器的收益都大，且零质量风险。

### 5. 本次未测（不装懂）
- Context-Gateway / leanctx / claude-shorthand / claude-slim：未跑（前者需代理部署，后几个需 Claude Code 配置面）
- chonkify：本机 pip 无可用轮子，装不上
- 中文压缩的下限：没找到能同时保住路径+编号+否定词的算法压缩器

## 五、明确不推荐
- 任何「把系统提示/规则压成摘要」的做法：规则一压就丢边界，属于降质。
- 直接上 20x 级压缩跑生产：学术口径，生产上先用 40% 试。
- 逐线自建压缩器：统一走一层，否则维护成本超过省下的钱。
