### 诊断报告：Peer Sync 验证失败

#### ① 最可能的根因
**密钥混淆导致的匹配逻辑错误**。
系统根据交付物文件名 `peer-sync-bm-c-20261111.md` 提取了接收方标识符（BM-C），并据此查询凭证表。然而，该 BM-C 节点尚未生成对应的 JSON 型回执（如 `PEER-SYNC-bm-a-...json`）。系统错误地将未存在的“接收方”状态映射到了不存在的“发送方”或中间态凭证上，导致验证逻辑误判为“匹配成功”，进而触发自动重试。由于实际业务状态缺失（无 JSON 回执），该机制无法通过校验即被阻断，且重试次数已达上限（2），表明此为一个持续性的数据不一致问题，而非偶发网络波动。

#### ② 下一步具体动作

*   **谁执行**：
    *   **后端运维工程师**（针对数据层）
    *   **QA 测试工程师**（针对业务逻辑）

*   **做什么**：
    1.  **人工核验凭证状态**：查询数据库或配置中心，验证节点 `bm-c` 是否已生成任何形式的同步回执文件。确认该节点当前处于 `UNVERIFIED` 还是其他中间态。
    2.  **修复匹配逻辑**：修改验证函数逻辑，将“名称模式匹配（Name Pattern）”作为第一级过滤条件，若未命中对应格式的凭证（JSON/MD），直接抛出 `NO_MATCH` 错误，禁止进入重试流程；仅当存在有效凭证时才进行签名校验。
    3.  **手动触发初始化**：在修复逻辑前，需为 `bm-c` 节点手动创建一份符合命名规范的正确回执文件，重置该任务状态，以便验证新逻辑是否生效。

*   **怎么验证**：
    *   重启或重载服务配置（Apply Config），观察任务状态日志，确认该卡件未再触发“重试 2"的自动循环，而是直接进入 `FAILED_WITH_REASONS` 状态。
    *   检查应用后的修复逻辑后，新提交的任务是否准确识别到“无对应 JSON 文件”并立即阻断流程，不再尝试匹配错误的凭证 ID。
