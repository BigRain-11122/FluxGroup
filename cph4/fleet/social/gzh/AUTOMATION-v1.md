# 全流程自动化地图 v1（2026-11-25）

> CEO 令：「我想全部自动化流程，不要我来操作。」
>
> 本文不是计划，是**现状清单**：哪几步已经机器做、哪几步半自动、哪两步在技术上过不去。
> 不许把「做不到」写成「待优化」。

## 一、11 个环节的自动化状态

| # | 环节 | 状态 | 谁做 | 工具 |
|---|---|---|---|---|
| 1 | 定位当季 / 今天写哪类哪题 | ✅ **全自动** | 机器 | `gzh_theme.py` + `gzh_schedule.py` |
| 2 | 抓热点判插队 | ✅ **全自动** | 机器 | `gzh_hot.py`（仅百度热搜可用） |
| 3 | 取素材（官方/媒体/设计站） | ✅ **全自动** | 机器 | `night_harvest.py`（46 个可用源） |
| 4 | 写稿 | ⚠ **半自动** | 机器出草稿，人定稿 | `gzh_daily.py`（有模型时）；无模型只出骨架 |
| 5 | 标题打分 | ✅ **全自动** | 机器 | `gzh_title.py` |
| 6 | 六道闸 | ✅ **全自动** | 机器 | 结构/事实/逻辑/去AI味/撞车/标题 |
| 7 | 排版 | ✅ **全自动** | 机器 | `gzh_render.py`（doocs/md） |
| 8 | 配图制作 | ❌ **手工** | 人 | 截图 + 红框标注（未脚本化） |
| 9 | 落盘 + 入待发队列 | ✅ **全自动** | 机器 | `gzh_daily.py` |
| 10 | **发布到公众号** | ❌ **必须人** | 人 | 见第四节，技术硬墙 |
| 11 | 数据回填 + 周复盘 | ⚠ **半自动** | 机器算，人报数 | `gzh_metrics.py`（抓取需登录态） |

**7 个全自动 / 2 个半自动 / 2 个必须人。**

## 二、一条命令的日常（除发布外全跑完）

```bash
python3 Tools/fleet/gzh_daily.py            # 今天
python3 Tools/fleet/gzh_daily.py --hot      # 允许热点插队
```

它会依次做：定位当季 → 取今天该写的类型与题目 → 抓热点 → 写稿（没模型就出骨架）
→ 结构闸 → 落 `drafts/YYYY-MM-DD/`（draft.md / gates.txt / manifest.json）
→ 入 `state/PUBLISH-QUEUE.jsonl`。

**没模型时它不会假装写完**：产出标 `NEEDS-MODEL` 的骨架，把三行骨架 + 该类型的
章节结构列到能照着写的程度，明确写「不许把这些提示语当正文发布」。
理由：占位文字混进队列，比没写出来危险得多。

## 三、两处「必须人」的真实原因

### 3.1 扫码登录（每天/每 4 小时）

- 实测：公众号后台会话 **4 小时过期**；微信不提供个人号长期令牌。
- 我们已试过：`setprofile` / `modifysignature` 直连失败；清 cookie 重扫换 token 仍被权限墙拦。
- **不是我不做，是微信的机制**。要彻底免掉，只有两条路：①企业号/服务号走认证接口（要主体资质）
  ②第三方服务商（要授权，且有账号风险）。

**能压到的极限**：每天早上一次扫码 → 当天 4 小时内所有自动化动作共用这个会话。
按「每天发 1 篇」的节奏，**一天一次扫码就够**。

### 3.2 点最后那次「群发」

- 群发是**对外不可逆**动作：点下去就推给所有粉丝，撤不回（订阅号每天 1 次额度也用掉）。
- 我可以把流程做到「填好标题、贴好正文、传好图、停在发送前一步、截图给你看」，
  但最后那一下我建议保留给人——**这不是能力问题，是责任边界**。
- 如果你要我连这一下也自动：技术上可行（Playwright 点按钮 + 确认弹窗），
  但需要你明确说「允许自动群发」，且我会加三道保险（首发禁发、内容含 NEEDS-MODEL 禁发、
  与队列不一致禁发）。

## 四、发布自动化的技术现状（诚实）

| 能力 | 状态 | 说明 |

| 静默操作后台（不动鼠标） | ✅ 可用 | `silent_browser.py`（headless + 独立 profile） |
| 自动填标题/正文 | ⚠ **未实测** | 后台编辑器是富文本，需实测粘贴路径 |
| 自动上传配图 | ⚠ **未实测** | 需实测 file input 与素材库路径 |

**结论：我没有把「自动发布」写成已完成，因为没实测过。**
下一步该做的是：拿一个测试草稿走一遍「填稿 + 传图 + 存草稿」，能做通再谈自动群发。

## 五、建议的自动排班（launchd）

| 时刻 | 任务 | 说明 |
|---|---|---|
| 07:00 | `gzh_daily.py` | 出当天骨架/草稿 + 过闸 + 入队 |
| 09:30 | `gzh_metrics.py --record --at 2h` | 前一晚发的稿，2 小时数据 |
| 次日 07:30 | `--at 24h` | 24 小时数据 |
| 第 3 天 | `--at 72h` | 72 小时数据 |
| 周日 20:00 | `gzh_metrics.py --weekly` | 周复盘 + 下周建议 |

**注意**：`07:00` 的 daily 会撞上平台的公众号时隙规则（90 分钟一档轮转）。
时隙管的是采集/浏览，**发布不受它约束**（发布是我们主动发起的对外动作）。
所以 daily 只要不跑采集就不会被时隙拦。

## 六、要做到「真的不用你操作」，还差三件事

| # | 差什么 | 卡在哪 | 解法 |
|---|---|---|---|
| 1 | 自动写稿 | 语料 19/200 未达门槛；`TRAIN-EXCLUSIVE` 占用 GPU | 先把语料收到 200，或直接用云端模型只写快评 |
| 2 | 自动配图 | 截图标注未脚本化 | 我可以写：截图 → 自动加红框与编号 → 导出 900×383 封面 |
| 3 | 自动发布 | 见第四节 | 先实测「填稿→存草稿」，再谈群发 |

**优先级我建议：2 → 1 → 3。** 理由：配图是纯机械活（我能全包），写稿卡语料，
发布卡授权与风险——而配图做掉之后，你每天只剩「扫码 + 点发布」两个动作。

## 七、诚实边界

4. **数据回填的自动抓取未实测**：`--fetch` 现在只会如实告诉你「需要登录态」，

# 补记：审核 / 上架 / 审美三条自动化的落地（2026-11-25 晚）

CEO 追加令：「不仅要自动化，还要审核自动化、上架自动化、审美自动化」。

## 九、审核自动化：把「人通读全篇」变成「人只看红项」

审核自动化的正确形态不是「机器说能发就能发」，而是**机器把红项挑出来，人只判红项**。

| 层 | 机检什么 | 工具 |
|---|---|---|
| 结构 | 篇幅/段落/小标题/数字密度 | `gzh_article_check.py --mode short\|long` |
| 事实 | 每个数字有没有来源 | `gzh_fact_check.py` |
| 逻辑 | 论点无据/因果倒置/以偏概全/循环/矛盾 | `gzh_logic_check.py` |
| 语言 | 客服腔/公文腔/空承诺 | `deai_check.py` |
| 重复 | 同号 30 天 / 同平台跨号 | `cross_account_dup.py` |
| 标题 | 长度/句式/禁词 | `gzh_title.py` |
| **图** | **封面比例/清晰度/文字密度/截空/红框标注** | **`gzh_visual_check.py`（新）** |
| 归属 | 这篇属不属于当季 | `gzh_theme.py --check` |

**人只需要看两类**：①闸判红的项 ②审美闸只能 WARN 的「好不好看」。
其余不用看——这也是为什么闸必须先跑完再看稿。

## 十、审美自动化：能算的算，不能算的说清

`gzh_visual_check.py`（自检 5/5）把「审美」里客观可测的部分算出来：

| 指标 | 判据 | 抓什么硬伤 |
|---|---|---|
| 封面比例 | 900:383 ±3% | 传上去被裁掉一块 |
| 封面宽度 | ≥600px | 手机上糊 |
| 边缘密度 | ≤20% | 字/元素太密，缩到手机上一团 |
| 有效对比度 | ≥3.0 | 看不清主次 |
| 主色数 | ≤6（WARN） | 配色杂 |
| 单色占比 | >95% **且** 无边缘 | 截空/白屏 |
| 清晰度 | Laplacian 方差 ≥60 | 糊图 |
| 红框像素 | ≥0.08% | 没标注，读者不知道看哪 |
| 整屏尺寸 | ≥1000×1000（WARN） | 该裁到一个动作的范围 |

**两次实测纠错**（都记在代码注释里）：
1. 「文字占比」原来用「近黑/近白像素占比」当代理 —— 深色封面直接算出 100%，判红。
   改用**边缘密度**（文字制造细边，色块不制造）。
2. 「截空」原来只看单色占比 —— 深色模式 UI 截图背景常占 80%，被误判成截白屏。
   改成**双条件**：单色 >95% **且** 几乎没有边缘。

**不能机检的（必须人看）**：氛围、调性、情绪、这张图「是否让人想点」。
工具不假装能判这些，只保证不发出去低级错。

依赖：Pillow（已装 `.venv-housing`）。用系统 python3 跑会明确报错并给命令，不静默降级。

## 十一、上架自动化：默认停在存草稿，三道保险才允许群发

`gzh_publish.py`（自检 7/7）：

| 档 | 行为 | 风险 |
|---|---|---|
| `--dry-run`（默认） | 打开后台 → 填标题 → 贴正文 → 存草稿 → 每步截图 | 无（不发出） |
| `--live --yes` | 真群发 | 不可逆 |

**三道保险（缺一不发）**
1. **首发禁发**：该号 PUBLISHED 台账为空 → 拒绝（第一次必须人看着发）
2. **NEEDS-MODEL 禁发**：manifest 状态不是 READY（骨架稿）→ 拒绝
3. **哈希一致**：正文 sha 必须等于入队时记录的 sha → 拒绝「队列是 A、发的是 B」

**诚实说明**：后台选择器**未实测**。所以流程拆成 10 个带名字的步骤，
每步单独报成败——失败会说「第 N 步 <名字> 挂了」，不会假装成功。
选择器集中在 `STEPS` 一处，实测一次后只改那里。

## 十二、现在的完整自动化链

```
07:00  gzh_daily.py          定位当季→取题→抓热点→写稿(或骨架)→结构闸→入队
       ↓（人：补正文、做配图）
       gzh_visual_check.py   审美/配图硬伤闸
       ↓
       五闸连跑              事实/逻辑/去AI味/撞车/标题
       ↓
       gzh_publish --dry-run 填稿→存草稿→截图（不发出）
       ↓（人：看一眼截图）
       gzh_publish --live --yes  群发（需三道保险）
       ↓
       gzh_metrics --record  2h/24h/72h
       ↓
周日   gzh_metrics --weekly  完读率排行 + 下周两条建议
```

**剩下的三个手工点**：写正文（等模型）、做配图（可脚本化，下一步）、点群发（责任边界）。
