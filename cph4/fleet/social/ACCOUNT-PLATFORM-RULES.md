# 账号与平台规则（可扩展到多号多平台）

> 2026-11-20 立。CEO：「以后可能号越来越多，平台越来越多」。
> 本文件是**规则正身**；参数在 `ACCOUNT-PERSONAS.json`，判据在代码里带自检。
> 一句话原则：**加号只改配置、加平台只加驱动，不改调度与判据。**

## 一、四层规则（越往下越具体，冲突时上层优先）

| 层 | 管什么 | 落点 | 谁改 |
|---|---|---|---|
| **L0 平台红线** | 跨平台导流、删重发、引战、刷屏、绕过风控 | `user_agent.guard()` + `OFFSITE/CONFLICT/AD` | 只许变严，不许放宽 |
| **L1 账号配额** | 每号每天 评论/弹幕/点赞 上限、养护期分级 | `ACCOUNT-PERSONAS.json` 的 `caps` | 按实测调，改一处在配置 |
| **L2 会话节律** | 活跃时段、单场 8–35 分钟、场间 15–60 分钟、2–6 点不活动 | 人设 `hours` + `agent_daemon.py` | 随人设定 |
| **L3 动作配比** | 看多动少：点赞 ≤60% 视频数、说话 ≤30% | `plan_session()` + `plan_violates()` | 代码内固定，改需依据 |

**冲突处理**：L0 永远优先；L1 与 L2 冲突时取更保守的一侧；L3 不参与冲突（只是配比）。

## 二、账号 = 一条记录（加号不改代码）

```json
"acctN": {
  "platform": "bilibili",
  "profile": "~/.fluxgroup/browser-acctN",   // 每号独立浏览器目录
  "mid": 123456, "uname": "昵称",
  "persona": "acctN",                        // 人设模板名（可多号复用）
  "primary": true,                           // 同 mid 只留一个主 profile
  "created_at": "2026-11-20T23:00:00"        // 养护期从这里算
}
```

**加一个号（3 步，永不碰密码）**
```
python3 Tools/fleet/bili_login.py --new acct4          # 建独立 profile 并登记
python3 Tools/fleet/bili_login.py --account acct4      # 有头浏览器，人工登录一次
# 然后在 PERSONAS 里加同名条目（领域/时段/配额/弹幕风格）
```

**调度自动跟随**：`agent_daemon.py --account acct4` 一个进程管一个号；
开机自启用 launchd `com.fluxgroup.agent-acct4`（照抄 acct1 的 plist 改两处即可）。

## 三、平台 = 一个驱动（新平台不改调度）

平台差异全部收在五个原语里，调度/节律/配额不感知平台：

| 原语 | B站现状 | 新平台要做什么 |
|---|---|---|
| `login` | `bili_login.py` | 登录取 cookie，写同一份 profile |
| `browse` | `browse_video()` | 打开内容页 + 停留 + 滚动（可顺带采集） |
| `like` | `/x/web-interface/archive/like` | 平台点赞接口 |
| `talk` | `send_danmaku()` | 弹幕/评论区的短互动，**没有就标记不支持** |
| `comment` | `practice_tick` 出稿链 | 平台评论接口 + 自己的闸 |

**硬规则**：平台没实现就不许跑。`user_agent.run_session()` 见到 `platform != bilibili`
直接返回 `尚未实现动作原语`——绝不把 B 站动作套到别的平台（那是假活，比不跑更糟）。

## 四、冲突矩阵（谁可以和谁同时跑）

| 组合 | 允许？ | 理由 |
|---|---|---|
| 同平台·不同号·浏览 | ✅ 允许 | 不同 profile、不同内容 |
| 同平台·不同号·动手（赞/弹幕/评论） | ⚠️ 允许但不碰同一内容 | 同 IP 同内容互动是最强关联特征 |
| 同号·两个 profile | ❌ 禁止 | 自造两套设备指纹（`_mid_lock` 拦） |
| 同平台·同 profile | ❌ 禁止 | 浏览器单例锁（`_profile_lock` 拦） |
| 跨平台·任意号 | ✅ 允许 | 平台之间无内容交集 |
| 训练 vs 会话 | ❌ 互斥（时间片） | 一块 GPU：训练中生成 2.1 vs 空闲 25.7 tok/s |

## 五、这台机器的容量上限（有依据，不是拍脑袋）

- 内存：训练 3GB + 4B 推理 4GB + 系统 ~8GB = 15GB，余 ~17GB
- 每个 Chromium profile 常驻约 0.4–0.7GB → **同时最多 2–3 个浏览器**（今天两号并行实测稳定）
- GPU：只有一块 → 训练与会话永远互斥
- **结论：单机同平台建议 ≤3 个号；超过 3 个要分机器或分网络，否则同 IP 关联风险与内存都会顶**
- 平台维度可叠加：不同平台可以各自开，但受同一虚拟机内存约束

## 六、加号的检查清单（缺一条不许上）

1. `platform` 有实现（否则只登记不跑）
2. 独立 `profile` 路径，且与任何现有号不重复
3. `persona` 存在，且**弹幕风格不与其它号共用**（共用=一个人开两号）
4. `created_at` 已写（养护期靠它算）
5. 登录态核验通过（`bili_login --check`）
6. 配额与现有号错开（同质配额的两个号 = 同一行为的两个副本）

## 七、扩展时要守的三条

1. **规则只许变瘦**：新增闸必须同时给"它能红"的负控与失效条件，否则就是加噪音。
2. **判据必须能读到"没有"**：平台未实现、账号未登录、段无件——都要显式返回原因，不许静默假跑。
3. **一张表管到底**：加号/加平台只动 `accounts.json` 与 `PERSONAS`，不动 `agent_daemon`/`user_agent` 的调度逻辑；
   若某次扩展必须改调度，说明抽象漏了，先补抽象再加号。
