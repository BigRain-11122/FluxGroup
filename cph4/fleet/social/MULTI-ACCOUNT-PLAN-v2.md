# 多号运营规划 v2（2026-11-25 · CEO 令「本机要运营的号非常多」）

> 前情：v1（`MULTI-ACCOUNT.md`）解决的是 **B 站两个号怎么不互相关联**。
> 本机现在的约束变了——要运营的号**很多**，所以 v1 的答案不够用：
> 「不同时、不碰同视频」只防得了一个平台内的两个号，
> 防不了「同一个稿子发到五个平台的五个号」。

## 一、先把真实边界量出来（不是猜）

| 边界 | 实测值 | 出处 |
|---|---|---|
| 单次出稿闭环 | 中位 **127s**（gen 16s / post 77s），最慢 316s | `state/GUARD-SENDS.json` SD08，近 10 拍 |
| 单号两帖最小间隔 | **12 分钟** | `FREQ-POLICY.json` min_gap_min |
| 单号日上限 | **39 条**（标注「人类量级」） | `FREQ-POLICY.json` max_per_day |
| 跨号动作最小错开 | **10 分钟** | `MULTI-ACCOUNT.md` cross_gap_ok |
| 夜间静默 | **1–6 点零动作** | `social_guard.py` AC04 |
| GPU | **单卡，训练与推理不并发**（训练中 2.1 vs 空闲 25.7 tok/s） | `COMPUTE-PLAN-20261120.md` |
| 内存 | free < **1500MB** 禁止新开浏览器 | `res_alloc.py` FREE_MIN |

## 二、容量结论：瓶颈不是算力，是时段错开

这点反直觉，但算术很清楚：

- 可用窗口 6:00–24:00 = **1080 分钟**
- 全机任意两帖至少间隔 10 分钟 → 理论极值 **108 帖/天**
- 留一半余量给训练、采集、人工干预 → 实用 **54 帖/天**
- GPU 侧：54 帖 ×（16s 生成 × 4 候选）≈ **58 分钟**，完全不是瓶颈

所以约束是 `号数 × 每号日发帖数 ≤ 54`：

| 每号每日 | 可运营发帖号数 | 说明 |
|---|---|---|
| 20 条（重号） | **2–3** | 接近 39 上限，几乎吃满窗口 |
| 10 条（正常） | **5** | 推荐稳态 |
| 6 条（轻号） | **8–9** | 场次稀，要盯 AC01「活着但没动」 |
| 只读不发的采号 | **+2–3** | 不占发帖时隙，但占浏览器内存 |

**结论：本机稳态 5 个发帖号。** 想上 10 个以上只有两条路——
降频（每个号变成"有号但不动"，会被 AC01 判假活）或**分机**。
调参数调不出来。

## 三、四个超载信号（都能机检，不全靠自觉）

1. 同号相邻两场间隔 < 12 分钟 → 节律被压
2. 全机相邻两帖 < 10 分钟 → 关联风险
3. AC01「活着但 14h 没动作」条数上升 → 场次被稀释
4. swap 增长或 free < 1500MB → 内存先死

## 四、三个真缺口（按风险排序）

### P0 跨号撞车闸 —— 规则写了，没实现

`MULTI-ACCOUNT.md` 写着「重复内容闸（7 天内 6-gram 重合 ≥60% 判重）」，
但代码里只找到 `social_comment_gen.shared_run()`——那是**评论**的 8 字重合原语，
作用域是「本批 + 本机语料」，**没有**任何东西检查「这篇文章是不是已经用别的号发过」。

这是多号运营最容易死的地方：平台判搬运不看你是不是同一个人，
五个号发同一篇＝五个号一起降权。而且它比风控更隐蔽——
风控会给你提示，搬运判定不会，只体现在后续每条的推荐量上。

### P1 排班粒度错了 —— 现在是「平台」不是「号」

`res_alloc.PLATFORMS` 里 `bilibili` 是一条，但实际有 `acct1`/`acct3` 两个号。
号少的时候没差别（两个号同平台，轮到一起就一起干）；
号多了以后，排班必须按**账号实例**轮转，否则会出现
「今天 B 站排了 8 次，实际两个号各只跑了 4 场，都低于人类节律」。

### P2 公众号链路零账号概念

`gzh_title.py` / `gzh_outline.py` 等全部硬编码 `gzh/TOPICS-v4.json`。
开第二个公众号，要么复制一份代码，要么改常量——两个都是债。

## 六、诚实边界

- 容量表里的「每号每日 10 条」是**从 FREQ-POLICY 的 39 上限往回收**的估算，
  不是实测出来的最优值。真实最优要等有 3 个以上号跑过一周才标定得出来。
- 「本机 5 个号」不含 IP 风险。同一出口 IP 上 5 个号已经是平台侧的关联信号，
  要做到 10 个号真正安全，必须换网络或换设备——这不是软件能解决的。
- 跨号撞车闸只能判「字面重合」，判不了「同一篇换个说法重发」的语义搬运。
  语义级查重要模型，等模型放开再说，现在先把字面这条守住。

# 附录：平台维度（2026-11-25 补 · CEO 令「平台也非常多」）

## 七、平台多的真正含义：不是加法，是乘法

号多 = 加法（多几个号，分时隙）。
平台多 = **乘法**——同一篇内容要拆成不同形态，每个形态都要单独生成、单独过闸。

## 八、9 个平台的真实发布能力（不是名单，是能不能发）

| 平台 | 读取 | 发布 | 发布方式 | 拦在哪 |
|---|---|---|---|---|
| B站 | ok | **ok** | api_write | 需开放平台稿件权限 + OAuth（唯一自动可发的） |
| 公众号 | ok | need-account | 后台手动 | 个人号无群发接口，只能后台粘 |
| 今日头条 | ok | need-account | 待核 | 没号 |
| 车家号 | ok | need-account | 待核 | 没号 |
| 知乎 | need-login | need-account | manual | 没号 |
| 微博 | need-login | need-account | 待核 | 没号 |
| 小红书 | untested | need-account | manual | 没号 |
| 抖音 | untested | need-account | api_write | 需视频发布权限 + 应用审核 |
| 视频号 | untested | need-account | manual | 没号（依附公众号，要绑） |

**结论：现在真正能发的只有 2 个**（B站自动、公众号手动）。
其余 7 个都是「没号」或「没权限」，不是我调参数能解决的。

## 九、内容形态的乘法成本（可算，不是估）

| 形态 | 字数 | 从哪来 |
|---|---|---|
| 公众号长文 | 3600 | 原创 |
| 头条 | 0 | 直接复用长文，只改标题 |
| 知乎问答 | 1200 | 长文改造：先结论后论证 |
| 小红书图文 | 400 | 长文改造：一个点 + 9 图 |
| 抖音口播脚本 | 1200 | 长文改造：60–90 秒口语 |
| 微博 | 140 | 长文改造：一句判断 |

- 单篇全形态 ≈ **6540 字**；按多候选择优 ×4 候选 ≈ 26160 token
- 本机实测 25.7 tok/s（空闲、4B）→ **约 17 分钟 GPU / 篇**
- 3 篇/天 → 51 分钟；加训练 2–4 小时，18 小时窗口内放得下

**所以 GPU 不是平台多的瓶颈。** 真正挡住的是下面两件。

## 十、真实瓶颈排序（这才是「平台非常多」的答案）

| 序 | 瓶颈 | 为什么软件解决不了 | 缓解 |
|---|---|---|---|
| 1 | **开号** | 7 个平台 need-account；规则「一天最多开 1 个平台」（同日同 IP 连开＝批量注册特征）→ **最少 7 天**，且要你的手机号收码、本人实名 | 我可以把每天开哪个号、名字候选、材料顺序排好，你只做扫码/填实名 |
| 2 | **登录态验证** | gzh 后台会话 4 小时过期（已实测）；多数平台重登要短信验证码 | 常驻 profile 减少重登；短信类只能你输 |
| 3 | 内容形态改造 | 要模型，且每条要过闸 | 17 分钟/篇，自动跑 |
| 4 | 时隙冲突 | 各平台高峰都挤在 20–22 点 | 错峰分配，见下表 |

## 十二、诚实边界（平台维度新增）

- 「9 平台并行」在软件侧成立，在**账号侧不成立**：现在只有 3 个发帖号、2 个平台可发。
- 抖音/快手走 api_write 需**应用审核**，个人主体大概率过不了，实际只能手动发。
- 小红书/知乎/视频号是 manual，意味着每条都要人工点发布——这是 CEO 的时间成本，不是机器成本。
- 微博发布方式仍标「待核」：没实测过，不许当成能用。
- 一稿改多形态后，各形态之间 6-gram 重合会很高（同一批事实与判断），
  `cross_account_dup.py` 对**跨平台**判 WARN 而不是 FAIL，就是为了不误杀这种正常复用。
