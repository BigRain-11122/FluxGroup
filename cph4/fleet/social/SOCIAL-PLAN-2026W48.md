# 养号线整体规划（2026-11-20 立 · 两号两智能体）

> CEO 指令：「两个号要不同的人设和侧重点」「不要这么保守，保证像 2 个人类」「技术上能并行就并行」
> 「我的机器就专门做养号，24 小时不停」「不要触发风控」「不要让我重复登录」
> 本文件是操作面正身；参数正身在 `ACCOUNT-PERSONAS.json` / `TUNE-PARAMS.json`，判据在代码里带自检。

## 一、什么叫"养好了"（可核验，不看感觉）

| 维度 | 指标 | 目标 | 现状取数处 |
|---|---|---|---|
| 账号健康 | 发送失败率 | < 10% | `USER-AGENT-LEDGER` 的 `send_fail` |
| | 登录态 | 每场核验通过 | `agent-*-.log` 无 `NEED-LOGIN` |
| 行为像人 | 每号每日场次 | 4–8 场 | ledger `session` |
| | 每号每日浏览条数 | 10–25 | ledger `watch`（daemon 台账） |
| | 点赞率（赞/看） | 20%–60% | ledger `like` / `watch` |
| | 弹幕 | 3–20 条/天（新号 ≤8） | ledger `danmaku` |
| | 评论 | 0–8 条/天（新号 ≤1 起） | ledger `comment` |
| 内容质量 | 评论过闸率 | ≥ 90% | `practice-log` 的 gate 结果 |
| | 重复率（7 天） | < 5% | `dup_recent` 命中数 |
| 训练 | 每段可用行数 | ≥ 400（稀薄段按 SUPPLY-TARGETS） | `social_loop --status` |
| | 判词功率 | n=30 | `TRAIN-LOOP-LEDGER.eval_n` |

**不做的事**：不删重发（折叠重发→5 日限制+关联视频降权）、不跨平台导流、不复读、不在同一视频下双号互动。

## 二、一天的排班（资源唯一冲突点是 GPU）

只有一块 GPU：训练与生成互斥（实测训练中生成 2.1 tok/s vs 空闲 25.7，差 12 倍）。所以按时间片独占：

| 时段 | GPU | CPU（可并行） | 说明 |
|---|---|---|---|
| 02:00–08:00 | **训练主窗**（1–2 轮，每轮 ~45 分钟 + 评测） | 烘焙 / 采集 | 两号不活动，GPU 全给训练 |
| 08:00–12:00 | 会话（acct3 9 点、acct1 10/12 点） | 烘焙 / 采集 | 会话期间训练让路（哨兵生效） |
| 12:00–18:00 | 会话（acct1 12/16 点、acct3 13 点） | 采集 / 补料 | 空隙可跑单轮训练 |
| 18:00–24:00 | 会话（acct1 21 点、acct3 20/23 点） | 采集 | 重点实战时段 |
| 2:00–6:00 | 不活动 | — | 两个号都睡（拟人） |

**仲裁机制**：智能体开一场会话 → 写 `state/AGENT-SESSION-<alias>`；训练侧看到哨兵（3 小时内）就让路。
反向：训练写 `TRAIN-EXCLUSIVE`，出稿侧（`practice_tick`）延后评论，只做浏览/点赞/弹幕（不吃 GPU）。

## 三、内存与并发预算

- 训练 3.0GB + 4B 推理 4.0GB + 系统约 8GB ≈ 15GB / 32GB。
- swap 目标 **< 2GB**（实测卸掉闲置 2b 后从 3.5GB 降到 1.84GB 且不涨）。
- 浏览器并发上限 2（两个 profile 各一）；不允许同 profile 双开。
- 烘焙 worker：夜间 4–7、白天 2（不与会话/训练抢核）。
- 禁止：训练窗口内加载 9B/8B（9GB 会直接把训练换出）。

## 四、两号分工（见 ACCOUNT-PERSONAS.json）

| | 老号 大喵没鱼吃 | 新号 许大喵去喵星 |
|---|---|---|
| 领域 | 自媒体 / AI / 短剧漫剧 / 数码科技 | 游戏 / 人工智能 / AI影视 / 娱乐 |
| 人群段 | peer_pro | shallow |
| 弹幕风格 | 点评手法（point） | 说感受（feel） |
| 时段 | 10/12/16/21 | 9/13/20/23 |
| 配额 | 评论8/弹幕20/赞50 | 评论5/弹幕14/赞40 |

**硬规则**：两号绝不共用弹幕模板；同一场不许重复同一句式；不碰同一条视频互动。

## 五、反馈回路（每天/每周）

1. **每日**：`user_agent.py --board` 出一屏（各号场次/观看/点赞/弹幕/评论/失败率）；
   异常（发送失败率高、登录态失效、某号连续零动作）→ 当日降档并报警。
2. **每周**：看两类死指标——①某号某动作长期为 0（等于没做）；②某段语料长期不涨（供给卡住）。
   处置只有两种：改配方 或 停掉该动作，**不允许留着空转**。
3. **规则只许变瘦**：新增闸必须同时给出"它能红"的负控与失效条件。

## 六、待校准（诚实标注，不假装已知）

- 新号养护阈值（第 0–1 天不评论）是保守起点，第 2 周用实测数据再定。
- 评论配额 8/天是上限不是目标；实际由"过闸率×可用视频数"决定。
- 弹幕模板各 5 条，长期会枯；需按周从语料里挖新句式（不许人工编）。
- 训练 n=30 的重复性尚未复测（同件两次是否稳定在 ±5 内）。
