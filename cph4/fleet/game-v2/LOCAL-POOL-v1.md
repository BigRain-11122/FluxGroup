# 本地模型池 v1（2026-11-20）

> 目的：把 CPU/内存用起来，跑不看重速度的后台活；GPU 只留一个交互模型。

## 一、三个槽位

| 槽 | 模型 | 设备 | 内存/显存 | 用途 |
|---|---|---|---|---|
| G | qwen3.5:9b | GPU | 6.2GB VRAM | 交互草稿、短任务 |
| C1 | qwen3.5:27b | CPU（num_gpu=0） | ~17GB RAM | 长文审阅、质量稿 |
| C2 | qwen3.5:4b | CPU | ~3.3GB RAM | 批量抽取、分类、校验 |

总占用约 **26.5GB RAM + 6.2GB VRAM**；当前 RAM 空闲 61GB，够。

## 二、并发规则

- 同时 ≤3 个后台任务；CPU 线程 27b=14、4b=4，留 14 给系统。
- GPU 只跑 9b；27b/4b 必须 `num_gpu=0`，不碰显存。
- 内存门限：空闲 ≥8GB；低于则停 C1。
- 构建/Unity 前：停 C1/C2，必要时停 G；构建优先。
- 任务不追求速度；排队跑，产出落盘。

## 三、任务类型

适合后台池：
- 长文审阅（矛盾/缺口/一致性）
- 批量抽取（房间、衣物、标签、JSON）
- 市场/竞品摘要
- 需求与文档对照

不适合：
- 交互式问答（用 G）
- 需要品味的终审（云端/人）
- 视频/图像生成（Comfy 独占 GPU）

## 四、产出与证据

- 每个任务落 `projects/fold-001/local/<job>.md|json`
- 记录：模型、设备、tok/s、耗时、输入摘要
- 失败重试 1 次；再失败落 `failed`，不无限重跑

## 五、命令

```
python Tools\gds\local_pool.py --run      # 跑 3 个后台任务
python Tools\gds\local_pool.py --status   # 看 ollama ps
```

## 五·五、实测坑（2026-11-20 22:3x 修订）

1. **多模型同抢会互相驱逐**：同机同时请求多个模型时，后加载的会把前面的挤掉。现在不靠"顺序换载"，靠**线程配额排队**。
2. ~~`num_gpu=0` 纯 CPU 不服务~~ **已作废**：2026-11-20 22:3x 实测，9b `num_gpu=0 num_thread=12` 跑 **8.0 tok/s**（RAM ~6GB）、27b **2.7 tok/s**（RAM ~17GB），都能正常出字。旧结论来自一次 Stopping 卡死，属瞬时态，不该写成规律。
3. 正法现在是**双车道**：GPU 独占 9b 做交互；CPU 用 `num_gpu=0` 跑后台审阅（9b 12T / 27b 12T，合计 24/32，留 8 给系统）。
4. 纯 CPU 调度与守卫=`Tools/gds/cpu_lane.py`（RAM <8GB 拒绝开跑，结果落 `audits/`，首轮报告 `audits/CPU-LANE-20261120.md`）。

## 六、一句话

**GPU 一个 9b 做交互，CPU 上 27b 做质量、4b 做批量；同时最多 3 个，构建优先，慢没关系，产出要落盘。**
