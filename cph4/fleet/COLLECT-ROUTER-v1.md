# 采集通道路由 v1（设备端统一化）

> CEO 令 2026-11-23：「以后找评论、公众号等各大平台的采集素材都走这个，你要科学梳理」。
> 本件定的是**走哪条通道**，不是"所有东西都改成设备端"。一刀切会把稳的换成脆的。

## 一、定标尺（先定原则，再定路由）

**"人眼看着页面才能拿到的东西 → 设备端（模拟器 App）；机器能签到的接口 → 接口。"**

三条理由：
1. **成本**：接口 0.1s/条、可分页、可增量；UI 抓 1–3s/条，且要等渲染。把接口能干的活搬到模拟器＝用 1/10 吞吐换更差的稳定性。
2. **稳定**：UI 抓依赖控件树，App 一改版就失效，需要每日冒烟；接口改了字段至少报错明确。
3. **合规**：有授权的开放接口本来就该用（抖音企业号有 `video.comment` 权限）；无接口的平台才退回"用户可见页面"读取，仍然只读、不点不赞不发。

## 二、现状盘点（通道 × 平台 × 工具）

| 通道 | 现有工具 | 平台 | 形态 |
|---|---|---|---|
| 浏览器（Chromium） | `social_collect.py` | B站/小红书公开页 | 滚动页面抽评论，无头优先，被风控提示改有头 |
| 公开接口 + 登录 cookie | `social_sweep.py` | B站 view / x/v2/reply / 弹幕 list.so | 批量补货，`social_riskguard` 控节奏 |
| 官方开放平台 | `social_douyin.py` | 抖音企业号 `video.comment` | 需凭据，**代码里没有写路径** |
| 消息中心接口 | `comment_harvest.py` | B站"别人回复我的" | 捞自己写过的评论原文 |
| **设备端（新）** | `android_farm.py` + `uiautomator dump` | 任意 App | 一实例一号，UI 树提取 |

已实测：`uiautomator dump` → pull → 解析文本节点这条路可用（`acct1` 上 8 个文本节点）。

## 三、路由表（这是要执行的规则）

| 素材 | 首选通道 | 兜底 | 判据/理由 |
|---|---|---|---|
| **公众号文章与留言** | **设备端（微信 App）** | — | 无公开接口；搜狗微信长期不可靠。设备端是唯一稳定路径 |
| **视频号** | **设备端** | — | 仅 App 内可见 |
| **小红书 笔记/评论** | **设备端** | 浏览器公开页（浅层） | 无开放接口，web 风控严（实测 300012） |
| **知乎 评论** | **设备端** | 浏览器 | 无头 mode 直接跳 `/account/unhuman` |
| **微博 评论** | **设备端** | 浏览器（需登录态） | web 端需登录 + 风控频繁 |
| **抖音 评论（企业号）** | **开放接口**（已有 `social_douyin`） | 设备端 | 有授权就别降级成 UI 抓 |
| **B站 评论** | **公开接口**（`social_sweep`） | 设备端补"需登录态才能看到"的深翻、风控页、用户主页资料 | 接口结构化且可分页；设备端只补接口拿不到的部分 |
| **B站 弹幕** | **接口**（list.so） | — | 量大、设备端无收益，明确不迁 |
| **已入语料库的存量** | 不重采 | — | 只做增量 |

**两条硬约束（沿用现有纪律，不因换通道而放松）**
1. **只读**：设备端也不点不赞不关注不发；发送永远走 `social_drafts` 出草稿 + 人工点。
2. **拿不到就记 UNKNOWN**：接口 412/风控 → 记 BLOCKED 并说明"转设备端"；设备端 UI 树没有评论节点 → 记 UNKNOWN。**任何通道都不许用 0 条冒充"该平台没评论"**。

## 四、设备端统一规格（"都走这个"具体长什么样）

1. **一实例一号**：`acct<N>` ↔ 平台账号一一对应，禁止一号多实例（两套指纹）。
2. **提取管道**（固定四步，缺证据不算成功）：
   `adb shell uiautomator dump` → `pull ui.xml` → 解析 `text/bounds/resource-id` → 归一化 JSONL。
   每次采集**必须留 `ui.xml` 原件**，JSONL 里带 `evidence=<ui.xml 路径>`，可复算。
3. **输出同构**：字段与现有语料一致（`platform/kind/text/author/like/ts/evidence`），`text` 必填；
   直接喂 `human_corpus.py --from-dir`，不许每个平台一套格式。
4. **动作层**：uiautomator2（或 Droidline）；**用 bounds/resource-id 定位，禁止坐标盲点**（改版即坏）。
5. **代理**：一实例一 SOCKS5（P2 落地后强制）；未配置代理前，多号不得同时采同一平台。

## 五、资源与排班（科学上限，不靠感觉）

- 设备端 **2 台常驻**（实测 1.6–1.9GB/台）＝本机安全值；第 3 台必须等 MLX 训练空闲（管理器已带内存闸）。
- 渲染用 `swiftshader_indirect`（吃 CPU 不吃 GPU），**GPU 留给训练/出稿**——与既有的"训练 vs 出稿互斥"不冲突。
- 节律沿用 `social_riskguard.wait_turn`（20–60s 抖动 + 会话休息）；设备端同样按人审节奏，不因"是自己的机器"就提速。

## 六、迁移顺序（每步带可核判据）

| 阶段 | 内容 | 验收判据 |
|---|---|---|
| **D0** | B站 App 装进 `acct1`，有头人工登录一次，存快照 | `uiautomator dump` 能拿到 App 首页 20+ 条视频标题 |
| **D1** | 设备端抽取器固化为工具（dump→parse→jsonl，留 ui.xml） | 同一页面跑两次，条数差 ≤10%，字段齐全 |
| **D2** | 小红书 + 知乎 各接一实例，跑通"打开→滚动 3 屏→抽 ≥30 条评论" | 两平台各产出 ≥30 行、evidence 齐全 |
| **D3** | 公众号通道：微信 App 登录后抽一篇图文留言 | 能抽到文章留言 ≥10 条并入库 |
| **D4** | 与现有语料池合并（`human_corpus --from-dir`），去重按 7 天 6-gram | 合并后重复率 <5%，`use=train` 正确标记 |

## 七、明确不做（防止"统一"变成"倒退"）

1. 不把抖音企业号接口改成 UI 抓（有授权、能分页、能增量）。
2. 不把 B站弹幕搬上设备（量大无收益）。
3. 不用设备端做"发送"（写行为仍只在 `social_drafts` 出草稿）。
4. 不在指纹未改造（P1 未过）时**多号同时登录同一平台**——那是自己给平台送关联证据。
