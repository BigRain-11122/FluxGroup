# 机队同步与联合工作：复盘与正解（2026-11-06）

## 一、先摆数字（都是盘上实测，不是印象）

| 指标 | 实测值 | 说明 |
|---|---|---|
| main 与 origin 分叉 | **落后 482 / 领先 85** | 任何 rebase/merge 都会打架 |
| 冲突高发路径 | cph4/fleet **223**、dispatcher 99、queue-receipts 78、lanes 34、chief 24、radar 18 | **96% 以上是运行状态文件**，不是代码 |
| 每日提交量 | 11-03 219、11-04 **722**、11-05 59、11-06 9 | 722/天 = 每秒 0.008 次，全是状态 |
| 直传通道 | tailnet_hub :8791（POST /status、/artifact）、fleet_bus 订阅 NATS、remote-receipts **65 条** | 通道本来就在跑，只是没被当成主路 |

结论：**不是"同步工具不够好"，是把 git 当成了三种东西的总线。**

## 二、根因：三种不同频率的东西挤在同一条分支上

1. **代码/工具**（Tools/*.py）：低频、需要版本审计、要冲突保护 → **该走 git**。
2. **运行状态**（队列/回执/lanes/心跳/雷达）：每台机每 45 秒写一次，
   高频、逐行追加、天然多写者 → **git 完全不适合**（每次都是整文件重写→必然冲突）。
3. **产物**（视频/图片/模型）：大文件 → **该走共享层**（asset_share/asset_pull 已建）。

把 2 塞进 1，后果是链条式的：
- 状态提交 → 分叉膨胀（482/85）
- 分叉一大会触发 rebase/merge → 有人 abort → **工作树回退，未提交的工具被删**
- 工具被删 → 监管脚本（supply_guard/demand_gen/tool_watch）集体哑火
- 哑火没人知道 → **"我不看就闲置"**
- 而补上的修复如果没入库，下一轮又被删一次（实测丢了 13 个工具）

## 三、正解：三条通道分开，各走各的

| 通道 | 承载 | 频率 | 谁写 | 冲突可能 |
|---|---|---|---|---|
| **git（单向）** | 代码、schema、配置、每日快照 | 低 | 人 + 主控 | 低（只有代码会冲突） |
| **直传 tailnet :8791** | 回执、lane 状态、心跳、产物 ≤4MB | 秒级 | 各机 → 主控 | 无（点对点，不合并） |
| **共享层 / assets + /media** | 素材、模型、大产物 | 按需 | 主控 → 各机自取 | 无 |

### 三条硬规则
1. **机队只 pull 不 push**。回执与状态走直传，不回写 git。
2. **状态目录不进 git**（下面已落地）：`state/`、`queue-receipts/`、`lanes/`、`radar/`、`chief/`、`sync/`。
   需要审计就按小时/天出一份快照提交，而不是每 45 秒一次。
3. **队列仍是权威账本，且只有主控写**；机队通过 pull 读卡、通过直传回结果。

### 验收指标（可机器判）
- `git rev-list --left-right --count origin/main...HEAD` → 长期 **0/0**
- 每日提交量 → **< 20**（现状 722）
- 冲突文件数 → **0**（现状 28）
- 远端回执条数 → 持续增长（现状 65）
- 四个监视器（pulse/supply_guard/tool_watch/useful_load）→ 全部有近期产物
