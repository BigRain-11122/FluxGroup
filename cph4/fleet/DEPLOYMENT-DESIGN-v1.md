> 依据：实测负载（不是文档抄来的）+ 一天四次撞车的教训。
> 一句话原则：**一台机器一个身份；常驻只在两处；写权只有一个；GPU 独占、CPU 多槽。**

## 二、部署四原则

1. **一机一身份**：控制面、模型面、生产面三者物理分开，不允许一台机同时当"派单的"和"干活的"。
2. **常驻只在两处**：Mac（控制面）+ bm-d（模型服务）。生产机**不装常驻 agent**，只按计划任务跑车道（跑完退出）。
3. **写权唯一**：共享账本（队列/配置/线路/令台账）只有 Mac 能写；生产机只写自己的产物与回执。这是四次撞车的正解。
4. **GPU 独占、CPU 多槽**：一块卡同一时刻只跑一图；CPU 按核数开 3–8 槽。

## 四、任务怎么落到机器（路由规则）

1. **按 needs**：`gpu` → 只去 bm-c（bm-d 入网后可分流 LLM 类）；`cpu` → 任意 CPU 机；`audio` → bm-b 优先；`light` → Mac。
2. **按时段**：bm-a 白天只接 `day_ok`；重 GPU 只在夜窗（22:00–07:00）。
3. **按库存**：每机常备 5 张可派卡，不足由 Mac 补；**跨机回落**只在同 needs 且目标机有空槽时发生。
4. **按独占**：GPU 卡带 `gpu_lease`，取不到就 DEFER，不许挤。
5. **按可靠性**：同一卡失败 3 次停线；同任务（去日期）不再造第 4 张。

## 五、Mac 的分档使用（已实装）

L3(≥14GB)/L2(≥8GB)/L1(≥4GB)/L0(<4GB 或 swap>600MB)：档位决定能不能加载 4B、能不能抽检与打标。**宁可少跑，不许换 swap。**

## 六、迁移清单（bm-d 本周入网后按序做）

1. bm-a 上的 35B coder 停服 → bm-d 起 llama.cpp（OpenAI 兼容，并发 10–16）。
2. Mac 的 4B 抽检改为调 bm-d；Mac 只留 embedding（300m）与规则判定。
3. 回测重批从 bm-b/bm-a 迁到 bm-d（256GB 内存吃得下）。
4. 代码代理/十席评审从各机散起改为统一走 bm-d。
5. 迁完复核：bm-a CPU 空槽回归装配、bm-d 并发槽 ≥10、Mac 内存余量回到 ≥20GB。

## 七、故障与兜底

1. Mac 挂 → `com.fluxgroup.watchdog` 拉起；连拉 3 次失败才报 CEO，期间生产机按最后一次派单继续跑。
2. bm-d 坏 1 卡 → 剩 2 卡照跑主力模型（降并发，不降质量）。
3. bm-c 卡死 → STALL 30 分钟释放，GPU 归零后重生；**不许**自动把 i2v 迁到 bm-a 白天。
4. 断电/断网 → 队列与账本在 git，恢复后按"最后 DONE + 未回执"重算，不重跑已完成的卡。

## 八、判定这套部署是否成立（可核）

1. 生产机上一个常驻进程都不许有（除系统与 lane 定时任务）。
2. 写权分层（现状与目标）：
   - **已达成**：Mac 主控脉不再做 rebase/merge/commit/push（`git.mode=off`），这是四次撞车的直接根因，已停。
   - **仍有风险**：生产机的 `lane_agent.git_publish` 仍推 main 且失败时会 merge origin。它只提交自己的产物与回执（`-- <paths>`），失败模式是"产物留在本机"，不是"别人提交消失"；但多机并发推 main 会产生拒绝与粉尘。
   - **目标**：生产机推到 `node/<name>` 分支，主控在安静窗口合并 main（S4 账房负责）。在此之前，禁止任何机器对 main 做 reset/rebase。
3. 每机空槽与库存差 ≤2（squeeze 与队列一致）。
4. GPU 独占：同时刻同机 GPU 卡 ≤1。
5. Mac 内存余量 ≥8GB 且 swap ≤600MB 常驻成立。
