## 三、把 18 条 P0 归并成 5 个结构性根因

单点看是 18 个 bug，通盘看只有 5 个错误假设：

### 根因 A：「一机一写者」只在写函数里声明，没在系统里成立
实际有五个写入口都在跨写：交接 `handoff`、命令面 `fleet_cmd` 三处、测试 `robustness`、主控巡查、`state_sync` 无 `--station` 的全量模式。表现=交接崩溃、分片被清空、冲突标记吞卡。
**正确形态**：跨工位只允许"追加意图"，不允许"改写他人工位文件"。交接改走 `outbox`（写自己分片的 `handoff_to` 行），目标机 SENSE 时读 origin 自行入队。

### 根因 B：「状态」没有单一权威
两套终态定义（`TERMINAL` vs `DONE_STATES`，ARCHIVED/SHELVED 行为相反）；`judge` 有 taxonomy 与卡级两处（本轮已堵降级，但仍是两处）；额度有静态估算与实测两处；调用账有两本。表现=8 种状态死卡、人判可绕过、额度算不清。
**正确形态**：一张显式状态迁移表（state → 允许的下一状态 + 触发者）作为唯一权威；`judge` 只由 taxonomy 决定；额度只认"实测账 + 速率外推"，静态估算降级为"设计上限提示"。

### 根因 C：「验证」是自己给自己发证明
自验=机器说完成，回执不带哈希、不带 judge；抽验拿不到卡（分片清空）或抽 0 件（判绿）。表现=12% 回执带 sha256、DONE 件里只有 1.1%。
**正确形态**：验收者独立取证——产物在盘 + 重算 sha256 与回执一致 + 回执带 rc 与 judge + 时间差 ≤10 分钟；缺任一项即 `PENDING_HUMAN`，不许 DONE；零抽验按失败计。

### 根因 D：「调度」是一张纸，没有身体，且分母只有 5%
19 条排班全绿但 44 个 LaunchAgent 全在 disabled/、无 crontab、无进程（本轮已改判 `PLAN-ONLY`）；59 道工序只有 3 道有命令。
**正确形态**：先把"一条工序端到端跑通一轮"作为唯一目标，再注册执行体；执行体注册必须是最后一步（先注册只会放大错误）。

### 根因 E：「身份」与「时间」靠推断，不靠证据
身份靠环境变量/hostname 推断（可伪造、可 fail-open）；新鲜度靠 mtime（git 操作即污染）。
**正确形态**：身份双证（本机只读身份文件 0600 + hostname，不一致即拒、导入失败即 fail-closed）；新鲜度读产物自带的 `_run.json.ts`（内容时间），mtime 只作辅助。

## 四、修序：依赖图决定顺序，不能按 P0 编号修

```
批次0（已完成）  闸修真能红 ──── 否则后面所有"修好了"都不可信
      │
批次1（地基，不改行为）  身份双证 + 状态迁移表 + 单一账本
      │                  ↑ 这三件不先做，claim/交接/reclaim 都在猜
批次2（安全边界）  命令白名单/去 shell=True + judge 单一权威 + root 不再是放行条件
      │
批次3（数据正确性）  claim CAS + 进程单例锁 + 坏行 quarantine + fsync + Windows 锁不降级
      │
批次4（链路闭合）  交接 outbox + reclaim 全形态 + FAILED/REVISE 退避重试 + 超时杀进程组
      │
批次5（供给面）  把 3/59 提到"至少一条线端到端"（见下），补齐该线的 selfdrive_cmd
      │
批次6（执行体）  注册调度 + 移除 v2 遗留（pulse 往已归档队列造卡）
```

### 每批的验收判据（可跑，不靠印象）

- **批次1**：伪造 `FLEET_STATION` 与 Identity 文件不一致时必须拒跑；`local_model` 损坏时 `write_queue` 必须抛错而不是放行；状态迁移表对 11 种状态给出确定的下一状态，非法跳转有负控。
- **批次2**：一张 `cmd` 含 `;`/`$( )`/`rm -rf` 的卡必须被拒；`judge:"MANUAL"` 与 `judge:"path"` 在人判工序上都是 `PENDING_HUMAN`（已完成）；传 `--root` 不再绕过护栏。
- **批次3**：3 进程并发 claim 同一张卡，执行次数必须 =1、回执 =1；SIGKILL 后重启无 `.tmp` 残留、无坏行洗白；Windows 模拟锁争用必须报错而不是无锁续写。
- **批次4**：跨工位交接后目标机下一轮 SENSE 能入队且本机不崩、日志有 `HANDOFF` 行；5 种 RUNNING 形态都能被回收；FAILED 在第 N 次后转 BLOCKED 并写缺什么。
- **批次5**：选定一条线（建议 `biggame` 提审包，产物契约齐全），端到端跑通 1 个产品：卡建→跑→验→回执带 sha256→抽验通过。
- **批次6**：排班 verdict 从 `PLAN-ONLY` 变 `排班在跑`，且首轮实测触发过一次（有 log 行）。

## 五、战略判断（最重要的一条）

**当前 v3 的真实产能是 0，且修执行层的 7 个 P0 不会改变这一点。**

原因：59 道工序只有 3 道有执行命令；3 条里 2 条产物已存在（判"做过"），1 条必败（`out/asset-pack` 不存在）。所以即使把 claim/交接/状态机/命令校验全修好，自驱每轮只会：建同一张卡 → 跑同一条必败命令 → FAILED → 不重建（状态机死胡同）→ 空转。

**因此通盘的优先级是**：批次 1–4 是"让链路不骗人、不崩"，批次 5 是"让链路有活可干"。**两者都做才有产出；只做前者仍然是零产出**。对外汇报与评分都不应把"闸全绿"当成"体系能干活"。
