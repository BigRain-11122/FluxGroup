# 一机多活的资源仲裁与平台轮转（2026-11-23 立）

> 触发：训练 + 双号会话 + 采集 + 发帖 + 本地模型同时跑，swap 涨到 4.4GB。
> CEO 令：「训练和实战并行，各大平台轮流」——不许为了稳而串行，也不许为并行而换页。

## 一、最重要的一条判据纠错：swap 不能当闸

**实测**：`sysctl vm.swapusage` 显示 used 4452MB，而同一时刻 `vm_stat` 算出的可用内存
（free+inactive+speculative）是 **15538MB**——机器根本没在换页。

**结论**：swap used 是**历史累计**，回落很慢；拿它当唯一判据会把"并行"永久锁死，
表现为"明明很闲却一直降档"。正法是**前馈看可用内存**，swap 只作背景记录：

| 可用内存 | 判决 |
|---|---|
| < 800MB | `DENY-NEW`：只收尾 |
| < 1500MB | `DRAIN`：训练可续，浏览器只收尾 |
| ≥ 1500MB | `PARALLEL`：训练 + 一条实战线 + 发帖 |

## 二、并行时真正的瓶颈是 browserd 单线程，不是内存

- 15GB 可用时开两个浏览器毫无压力（每浏览器约 700MB）；
- 但 `browserd` 单线程服务所有账号，**两个平台同时点会互相排队**（实测发帖排队 185 秒、post 77 秒）；
- 所以并行规则＝"训练常驻 + **一次只放一条实战线** + 发帖优先"，而不是"同时开所有平台"。

推论：任何"多加一个平台"的诉求，先问它会不会挤进同一个 browserd 队列；会，就必须分时片。

## 三、平台轮转规则

`Tools/fleet/res_alloc.py`（launchd `com.fluxgroup.resalloc`，600 秒一拍）：
读 swap／可用内存／训练／浏览器／模型 → 出班次 → 落 `state/RES-SLOT.json`。
`user_agent.run_session` 读该文件，降档时**直接不进**（不是跑起来再退）。

平台表（权重决定片数，90 分钟一片）：
- `bilibili` live 权重 5 —— 养号主线（看/赞/弹/评论/投币/收藏/关注）
- `gzh` building 权重 3 —— 采集通、供给待接；**不能出稿**
- `xhs` / `douyin` need-account —— 无账号不排班（自检里有一条专验"未开账号的平台不占片"）

**只有会话侧接了闸**；采集侧、训练侧尚未读班次文件——"轮到公众号的片子时 B 站自动让位"
这一步还没实现，别当成已完成。

## 五、群审六席的经验（值得复用）

派六席（内容工艺/平台合规/数据判据/自动化运维/采集工程/选题商业），要求只审不修、
必须真跑命令取证、写明验证了什么与没验证什么。**四席独立指向同一根因**：
**把"计划"当成了"已实现"**——
- 文档写"镜像源采集：自动做"，代码零实现；
- 自检写"uid 稳定"，断言是 `_uid(u)==_uid(u)` 恒真；
- 判据 7 条自检里 3 条恒真；
- 选题承诺"我实测 3 万公里"，实际无车。

**通用纪律：凡"声明"必须能在同一次运行里被证伪，否则只许标成计划，不许写进判据/清单。**
