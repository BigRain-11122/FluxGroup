# 养号/训练闭环的三类失效与修法（2026-11-25 ~ 11-26 实证）

> 索引目标：L1 记忆里只留一句指针，细节看本文件。
> 结论先行：这套系统最贵的浪费不是"没在跑"，而是"在跑但产出重复/永远被挡"。
> 判据一律用**产出指纹**与**产出龄期**，不用进程存活、不用 run 次数。

## 一、训练空转：三种不同机制，症状完全一样

症状：run 数很多、loss 稳定、台账在长，但模型没变。

| 机制 | 识别方法 | 实锚 |
|---|---|---|
| 临时作业固定配方 | `launchctl list` 里出现非 plist 的作业名（`fluxgroup.train.2400`），`launchctl print` 看 `program = /tmp/xxx.sh`、`runs=N` | 每 1.5h 重跑 `--data train-h5 --seed 20261117`，10 个 run 的 adapter SHA 全为 `c5ac19ef…` |
| 数据集不重建 | 比 `train-*/train.jsonl` 的 mtime 与 data_sha | train-h5 停在 11-24 12:52，隔天还在用 |
| 状态重建丢判据字段 | 读 LOOP-STATE：`recipe` 全为 None，而 `train_build.RECIPE` 有值 | `reconcile()` 只捞 last_ts/last_rc/rows，不捞 recipe；台账记录也不写 recipe → 每轮判「配方更新」放行 |

**唯一可靠的空转判据**：对不同 run 的 `adapter/adapters.safetensors` 取 SHA 前 16 位，看有几个不同的。
`唯一模型数 / run 数` 就是有效率。11-26 实测 7/17 = 41%。

**修法的两条硬规则**：
1. 状态文件是缓存、台账是事实 —— 凡是从台账重建，必须把**判据字段一起重建**（recipe、阈值版本、口径版本）。少一个字段，依赖它的闸就永远返回"该重训"。
2. 冷却必须先于"配方更新"判定。否则历史台账缺字段时，每段会立刻重训一轮（8 段 = 8 次白跑）。

## 二、锁的所有权打架：谁拥有浏览器必须只有一个答案

症状：日志反复打「让路：profile 在采集手里/xxx 秒后重试」，台账里对应动作恒为 0。

三条实测链路：
1. `social_collect._acquire_profile_lock` 里 `yield_ok and _human_wanting(prof)` 是**全局**判据（有 AGENT-SESSION 哨兵就让路），与具体 profile 目录无关 → 换成独立目录照样让路。正解：`FLUX_PROFILE_SUFFIX=-learn` + `FLUX_PROFILE_NO_YIELD=1`（自己的目录不需要让）。
2. `user_agent.like()` 自己 `_launch()` 浏览器，而 `browserd` 24 小时握着同一把锁 → 点赞/弹幕恒 0。正解：给 `browserd` 加 `like` 动作，走已登录上下文的同源 fetch（实测 1.9s），`like()` 先 `_daemon` 后回落。
3. **回落分支不还锁会反噬主链路**：`browse_video` / `send_danmaku` 的 fallback 里 `ctx.close()` 了却没 `release_profile_lock`。browserd 重启那一瞬，养号请求全落到 fallback，锁被养号进程攥住 → 之后**发评论**反而拿不到 profile。

**通用规则**：任何「抢锁 → 失败 → 自己开资源」的路径，`finally` 必须有对应的还锁；否则一次重启就能把主链路锁死。
**架构规则**：一个 profile 只能有一个持有者（此处 `browserd`），其余进程只下 HTTP 动作，不自己开浏览器。

## 三、停摆检测：用产出龄期，不用进程存活

学习曾断更 21 小时，而进程一直在跑、日志一直在打（每轮只打"让路"）。所以"进程在"毫无意义。

`loop_regression.py` 新增 L12 四线心跳：

| 线 | 判据文件 | 上限 | 为什么是这个数 |
|---|---|---|---|
| 训练 | `state/train-loop.log` **或** 最新 run 的 `train.log` | 45 分钟 | 循环 5 分钟一拍；但一次训练约 50 分钟且同步阻塞循环，那段时间只写 run 内 train.log，只看循环日志会每轮误报 |
| 学习 | `LEARNING-LEDGER.jsonl` | 90 分钟 | 1200s 一轮 + 采集耗时 |
| 实战 | `reply-log.jsonl` | 90 分钟 | 回复间隔 12 分钟 |
| 养号 | `USER-AGENT-LEDGER.jsonl` | 300 分钟 | 深夜最长歇 3 小时 |

取数坑：`train/RUNS` 下混着 `CMP-204622-500` 这类历史目录，纯字典序会排到"最新"，读到没有 train.log 的旧目录 → 误判停摆。只认 `^\d{8}-\d{6}$`。

## 四、两个容易误判的"看起来在掉"

1. **回复 33 条/天不是掉了，是撞策略上限**。`FREQ-POLICY.json` 写死 `max_per_day=39`、`min_gap_min=12`，理由栏原话"人类量级"。判据：拿当日回复数比 max_per_day（33/39 = 85% 用量），不要比历史峰值。
   效率反而在改善：11-25 是 1917 次尝试换 34 条（1.8%），11-26 是 382 次换 33 条（8.6%）。
2. **闸读错账**：`loop_regression` 的 L6「发帖」只数 `practice-log` 的 `action=post`，而实战写的是 `reply-log` 的 `action=reply`（带 `{"code":0}` 回执）。所以"今日真发 0"是读错面，不是没发。纪律：不许为了让闸变绿放宽判据，要改就改成认真实动作并写明依据。

## 五、B站环境事实（会反复踩的三条）

1. **`/x/v2/reply` 对本机返 412**，返回的是风控 HTML 页；而 `nav` 报 `isLogin=true`、`mid=388497033` —— 登录态是好的，是接口被挡。所以"用 API 查评论/回验"这条方案在这台机器上不通。
2. **正路是读渲染后的评论区**：视频页滚动加载后，遍历 `bili-rich-text`（含 shadowRoot）取正文。学习通道一直靠这个每小时采到 30+ 条，回验也改走它（`browserd` 的 `verify_text` 动作）。
3. **回验必须做正控+负控**才可信：正控用一个高频字（如"我"）必须 `visible=true`；负控用不可能出现的串必须 `visible=false`。只跑负控会把"取不到数"误当"不可见"。判据纪律：取不到数返 `None`，绝不与"确实不可见"混为一谈。

## 六、Playwright 提速：别等 `domcontentloaded`

`post_action_s` 历史中位 32.7 / 89.9 / 44.2 / 54.1 秒，全部超 30 秒上限。根因不是发帖逻辑，而是 `pg.goto(..., wait_until="domcontentloaded", timeout=15000)`：B站视频页长连接多，这步每页**吃满**超时，而发评论走的是同源 fetch，根本不需要 DOM 加载完。

改 `wait_until="commit"`（约 1 秒返回）：干跑 post 实测 **54.1s → 5.0/3.9s**。
配套坑：`commit` 之后 JS 环境偶尔还没切到新文档，`evaluate` 会抛 `Execution context was destroyed` —— 给一次 1.5s 短重试，别把导航时序问题算成发帖失败。

## 七、失败必须逐环节可辨（一句笼统话等于没报错）

`reply-log` 里 91% 都是「闸拒或无稿」，分不清是模型挂了还是稿子被闸拦。拆开后才发现**七种不同原因**：8788 不可用 / 模型返回空 / 长度不合 / 闸拒 / AI 腔 / 编造 / 跑题。

最隐蔽的一种：`generate_lora` 在服务忙时返回 `ok=False` + 空文本（不抛异常），调用方 `if not t: return ""` 直接静默吞掉。**任何"返回空就当无稿"的分支，都必须先把上游的 why 打出来。**

## 八、出稿闸标定（实测，不靠感觉）

工具 `Tools/fleet/gate_calibrate.py`：拿真实评论现场生成，按 长度/闸/AI腔/编造/跑题 逐环节统计，并打出共享二元组分布。

16 条实测：**通过 12（75%）**，跑题 4（25%），闸拒 0、AI 腔 0、编造 0、空文本 0、模型不可用 0。
共享二元组分布 `{0:2, 1:5, 2:2, 3:2, 5:1, 6:2, 9:2}`。

据此定口径（`_ontopic` 与标定器必须同口径）：
- 共享 0 → 必拒；
- 短中评（<12 个二元组，约 14 字内）→ 只需 1 个；
- 长评（≥12 个二元组）→ 需 2 个（长评里单个二元组太容易撞）。

反例（原口径）：按二元组数量 1/4 缩放时，9 字评论（8 个二元组）就要 2 个，等于要求 25% 重叠——自然改写做不到，实测把切题回复成片误杀。

**教训**：`min_human=8` 这类阈值在 reply face 上其实不拦人（标定闸拒 0%），真正卡量的是出稿成功率与**发帖供给**（`drafts` 通道 11-14 之后就断了，导致发帖 1 条/天）。所以"漏斗窄"要先分清窄在哪一环，别一上来就动红线阈值。

## 九、合规红线：模型会替公司许愿

抓到一条**已发出**的回复：「三连已收到，安装包和字体我打包发你，自取就好」——根本没有这个包。

`_fabricates` 原来只查数字与英文缩写，这类**交付承诺**全漏。新增 `_PROMISE`：
`打包|发你|传你|私信|自取|加我|给你发|转你|邮箱给你|链接给你|放群里|上传|置顶评论|评论区置顶|主页有|简介里有`，命中即判编造。

原则：不承诺、不导流、不索要联系方式，比"像不像人"优先。假的交付承诺是欺骗，比 AI 腔严重得多。

## 十、可复用的自检负控清单

- `reconcile` 必须保住 recipe；台账里确实没这个字段时才允许为空（不许编造）。
- 缺 recipe 但在冷却内 → 必须判不可训（否则"配方不明"成为绕过冷却的后门）。
- `like` / `verify` 缺参数必须在取上下文**之前**就拒，否则自检会被"profile 被占用"打断，测不到动作本身。
- 守护不在时动作必须回落返回 None（保证冷启动路径仍可达）。
- 空转判据要能红：把被检 run 的 adapter 换成另一个已知指纹，判据必须报"有效率 100%"。
- 标定器必须能把"生成失败/空文本"与"跑题"分开计，否则模型挂了会被记成判据问题。
- 回验必须同时有正控（必命中）与负控（必未命中）。

## 十一、音乐平台评论语料（CEO 2026-11-26 令）

CEO 令原话：「你的训练素材去拉 qq音乐 网易云音乐这些的音乐平台的评论，有很多高质量的」。

**为什么这条线值得单独记**：养号缺的不是干货腔，是情感短句。B站评论偏理性讨论
（"这期知识点密集"），音乐平台评论区偏故事与感受（"虽然叫晴天，但整个故事都在下雨"），
正好补上语料里最缺的那一类。

**两条通道（实测可用，`Tools/fleet/music_comments.py`）**：
- 网易云：`music.163.com/api/v1/resource/comments/R_SO_4_<id>?limit=&offset=` 直连，
  返回 `hotComments` + `comments`，无需登录、无需加密参数。
- QQ音乐：`c.y.qq.com/soso/fcgi-bin/client_search_cp` 拿 **数字 songid**，
  再用 `fcg_global_comment_h5.fcg?...&topid=<songid>&cmd=6&pagenum=` 取评论。
- ⚠️ 静默坑：`topid` 传 **songmid（字母串）会返回 code=0 但 total=0**，
  看着成功其实一条没有。必须用数字 songid。

**落盘与去重**：写入 `corpus/human/own_collected.jsonl`（`use=train` 才进训练集），
字段与既有行一致（h/text/src/license/use/kind/thread/origin/…），`h=sha1(text)[:16]` 去重，
同时留一份原始到 `raw/music/`。`MUSIC-SEEDS.json` 是 30 位歌手/乐队的轮换歌单，
`--rotate N` 按批轮换，launchd `com.fluxgroup.musiccollect` 每 6 小时跑 4 位。

**一个必须记住的坑**：音乐评论用词分散，靠信号词命中率极低——实测 2412/3073（78%）
落到 `generic`，而 `generic` **不进任何训练段**，等于白采。正法是给
`segments.classify(text, spec, hint=...)` 加可选来源提示，`corpus_bake` 按
`(text, seg_hint)` 传参。hint 仍走同一个分类器，不另立口径。
加 hint 后 `music_seeker` 段 480 → 3580 行（涨 7 倍），自然跨过"语料涨 10% 才训"的闸。

**口径变更留痕**：2026-11-17 旧令是"第三方语料 use=reference 永不进训练集"，
本次为 CEO 明令例外，已按 `use=train` 入库并保留 `src`/`license`/`thread` 便于回退。

## 十二、语料源扩展：从音乐平台到豆瓣（2026-11-26 续）

CEO 续令：「去找其他的平台语料投喂训练，要高质量的，打开思路」。

**判据先行**：模型短板不是知识，是像人说话（REJECT 多因「均分 -12.5」「人味退步」）。
所以只收**短、具体、有情绪、不总结的评论区表达**；长文章（知乎/公众号/影评长文）
一律低优先级——它们教模型写作文，而我们要的是接一句话。

**实测结论矩阵**（全文与逐条理由 = `cph4/fleet/social/CORPUS-SOURCE-MATRIX.md`）：
- ✅ 网易云 / QQ音乐 / 豆瓣读书短评 —— 三条已落地
- ❌ 豆瓣电影（302，加 Referer 仍返 3KB 提示页）、贴吧（403）、微博（302 需登录）、小红书/抖音（强签名）
- ⚠️ 虎扑（200 但正文前端渲染）、B站弹幕（接口通但只返 2 条，且弹幕是即时反应不是表达 → 不投入）

**一条纪律**：被挡住的不硬闯（登录墙/签名/验证码一律不绕）。绕一次的成本远高于语料价值，
还会把账号放进风控视野。实测代价：豆瓣连跑 250 本后 Top250 列表页直接 403（临时封），
说明"慢慢补"比"一次跑完"更符合平台节律。

**"头部"要可量化，不能靠榜单名次**：网易云热歌榜前十混着网络新歌（评论 5,516），
而真头部是评论量——晴天 1,969,847、我不难过 112,935。用 `--min-total` 筛。

**搜索结果第一条往往是翻唱**：搜「稻香 周杰伦」第一条是「稻香(治愈版)｜街道办GDC」，
「七里香 周杰伦」第一条是王俊凯版。按**评论量最大**挑版本（原唱碾压翻唱），
不要依赖歌手名匹配（正版 artist 有时写 "Jay" 不写"周杰伦"）。

**这轮踩到的三个通用工程坑**：
1. **共享落盘函数硬编码字段**：`to_row()` 把 `seg_hint` 写死成 `music_seeker`，
   于是豆瓣短评全被标成音乐区，`critic` 段一条没涨（1612 条白标）。
   教训：共用函数里的"来源相关字段"必须允许调用方覆盖，否则等于给所有源盖同一个章。
2. **长任务只在最后写盘 = 超时全丢**：250 本 × 2 页要 20 分钟，被 timeout 杀掉一条不剩。
   改成每本书采完立即入库并记进度（`FORUM-PROGRESS.json`），下次自动跳过已采。
3. **限流不退避**：豆瓣连续请求会 403。遇 HTTPError 退避 3 倍间隔，且不硬闯。

**新增产物**：`Tools/fleet/forum_comments.py`（豆瓣 Top250 自动发现 → 采短评 → 统一质量闸
→ 标 `critic`）、launchd `com.fluxgroup.forumcollect`（每 12 小时最多 60 本）、
`com.fluxgroup.musiccollect`（每 12 小时经典头部 + 热榜前 20，门槛 15 万评论）。

**语料规模**：80,739 行（自有 B站 72,091 / 网易云 6,435 / 豆瓣 1,612 / QQ 601）；
可用段：`music_seeker` 2,075（原 480）、`critic` 629（原 157）。

## 十三、第一轮"训练→验证"闭环与两处基础设施修复（2026-11-26 晚）

### 结论（有对照数字）

`music_seeker` 段（2,075 行，含音乐 + 豆瓣 + 网易新闻新语料）训练结果：
val 最低 **2.778**（该段历史 3.2–3.7）、判定 **KEEP**、均分 **+27.0**、人味 **+7.0**。

同一批 16 条评论、同一 seed 的标定对照：

| 模型 | 通过率 | 跑题 | 共享 0（自说自话） |
|---|---|---|---|
| 旧 adapter 复测 | 43.8%（7/16） | 56.2% | 7 条 |
| 新 music_seeker | **62.5%（10/16）** | 31.2% | **3 条** |

**方法论**（比数字更重要）：先跑基线 → 训练 → 切 adapter → 用**同一批样本 + 同一 seed**
复测。没有基线的"变好了"是空话；换样本的对比是噪声。
注意生成有波动：同一 adapter 两次跑可差 ±1 条，所以"通过率差异 <10pp 视同噪声"。

### 修复一：GPU 租约僵尸回收

实锚：`selfgen` 卡在 8788 连接上两小时（CPU 1.6%、无子进程），训练一直打
「GPU 让路：GPU 被占用：selfgen（已 7078s）」；随后 `practice_tick` 又卡在浏览器上
5 分钟不放，同样挡路。租约 TTL 写了 3600 秒，但"过期"只用于展示，**没人据此回收**，
因为 flock 由活着的进程持有。

修法：等待时若「超 TTL + CPU 空闲(<2%) + 名字在白名单」三条同时成立 → kill 并重试拿锁，
每次回收写 `state/gpu-lease-reap.jsonl`。只回收超时的，长训练合法占用不会被误杀。

**必须有的祖先保护**：子进程抢锁时，持有者往往正是它自己的父进程（父持租约起子进程干活），
那种"父进程 CPU 空闲"完全正常（它在等子进程）。不挡就会子杀父——自检里立刻红。

### 修复二：一个自检本来就是假红

`gpu_lease --self-test` 的「无继承的子进程必被拒」一直 FAIL，**旧版代码同样 FAIL**：
它只改了父进程的全局 `LOCK` 路径，子进程仍指向线上真锁，于是子进程必然拿到锁，等于没测。
改成用 `FLUX_GPU_LOCK`/`FLUX_GPU_REC` 环境变量把临时路径传给子进程，6/6 PASS。

**教训**：自检里凡是"起子进程验证隔离"的，必须确保被测状态真的传给了子进程。
只改父进程的全局变量，测的是空气。
