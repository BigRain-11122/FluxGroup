# 居民文案质量与语料检索 · 2026-11-17

CEO 当日两条硬要求：「文案要有人味、不做作、不要 AI 感、符合世界观与人设、千人千面」+
「本地模型调用这些语料要能快速找到」。本文记录诊断方法与两处修复。

## 一、诊断方法：查「意象频率」，不是查「AI 套话词」

抽样最近 3 小时写入的 89 条年轮，做两组统计：

**第一组（AI 套话词）**：仿佛 / 宛如 / 一丝 / 不禁 / 涌起 / 岁月 / 时光 / 治愈
→ **命中 0 条**。字面层是干净的，没有那种一眼假的书面腔。

**第二组（意象词频）**：

| 意象 | 命中率 | 判断 |
|---|---|---|
| **风** | **87%（77/89）** | ❌ 灾难级 |
| 旧 | 29% | 偏高 |
| 灯 | 20% | 可接受 |
| 云 | 16% | 可接受 |
| 汤 | 9% | 局部集中（6 条里 5 条用汤作比） |

**结论：「AI 感」的观感来源不是套话，而是意象单一。** 连着读十条、九条都在刮风，
读者立刻觉得"这不是人写的，是一个模板在批量填"。

**方法论**：判断文案是否千人一面，要统计「同一意象在当日语料里的覆盖率」；
单看禁用词表会漏掉这种"字面各异、骨架相同"的模板化。

补充观测：开场前 8 字分布是健康的（Top1 仅 3 次），说明开场骨架分配机制有效；
人设区分也真实存在（巡边员说"谁也别想从这眼皮底下溜进坏包"、盘口说"汤要趁烫，话要慢讲"、
画桌说"新进的资料边角已翻得发软"）。

## 二、根因：两个 prompt 块串联，后一个在喊停

`build_prompt()` 里原本是：

```python
f"{time_recap(sig)}{weather_recap(wx, seed=cid, ...)}{wx_skip_block(cid, sig)}"
```

- `weather_recap()` 给「风=风挺大」这类**具体措辞**，位置靠前、标注「最高优先级」
- `wx_skip_block()` 对约一半席次说「本轮不写天气」

两段**同时**出现 → 模型照写（措辞具体、位置更靠前、优先级更高）。
所谓「按 md5 分流一半席次不写天气」的机制**被完全架空**，实测 87% 写风正是这条的结果。

**修法（一行，`or` 短路互斥）**：

```python
f"{time_recap(sig)}{wx_skip_block(cid, sig) or weather_recap(wx, seed=cid, ...)}"
```

分流比例同时从 1/2 提到 **2/3**（1/3 保留天气护栏，防编造雨/风）。
验证：4/4 席互斥正确；67/100 分流比例符合预期。**预期风提及率 87% → 约 33%。**

**可复用判据**：prompt 里"先给素材、后说别用"的串联结构必然失效——
LLM 会采纳更具体、更近、优先级更高的那段。要互斥就必须在代码层短路，不能靠措辞劝退。

## 三、语料索引（`Tools/corpus_index.py`）

`memory_index.py` 只能按**单个居民**做 BM25 记忆召回（`--id X --q 主题`）；
全库定位此前只能 `os.walk` 10191 个文件。

新增 sqlite3 索引（零依赖、零 LLM，`state/corpus.db` 6.4 MB，已被 gitignore）：

| 操作 | 耗时 |
|---|---|
| 全量建（10111 人 / 20941 条年轮） | **4.1 秒** |
| 增量更新（只重扫 mtime 变化） | **0.25 秒** |
| 单居民查询 | **0.12 秒** |
| 关键词检索（如「风铃」） | **0.12 秒** |
| 城区 / 欠写筛选 | 0.1 秒 |

表结构：`citizens(id, district, species, prof, last_ring, ring_count, mtime)`
+ `rings(cid, date, text)`（正文已剥 [锚] 注脚）。

## 四、顺带解决产能瓶颈：选人面提速 30-50 倍

`due_citizens()` 原本每批 `os.walk(anchors + registry)` 共 **10612 个文件**（10-15 秒），
这是每批固定开销的大头。改为优先读索引：

| 口径 | 结果 |
|---|---|
| walk 版 id 数 | 10111 |
| 索引版 id 数 | **10111（完全一致）** |
| `due_citizens` 耗时 | **0.318 秒**（原 10-15 秒） |

**安全网**：索引缺失或查询异常一律退回 walk 路径——宁可慢也不能漏人。
`produce_pump.py` 每批前跑 `corpus_index --build`（0.25 秒）刷新，把索引滞后窗口压到一批内。

**产能影响**：单批从约 70 秒降到约 60 秒 → 约 540 → **630 条/小时**，
首轮全量 10114 人约 **20 小时**。

## 五、质量面计量（`produce_pump.py` 回执新增字段）

| 字段 | 含义 |
|---|---|
| `pass_rate` | 写入数 / due 数（净产出效率） |
| `skipped` | 被质量闸拒写数 |
| `soft` | 软让步数（落盘但带瑕疵标记） |

**为什么需要**：批席从 10 放大到 15 会让同批反模板约束更紧，写入率可能下降。
只有把 pass_rate 记进回执，才分得清「提速」和「提了速但净产出没涨」。
判据：若 batch15 的 written/小时 ≤ batch10 实测值（350-400），回退 12。

## 六、批策略沿革（`Tools/batch-policy.json`）

6（2026-09-24 P-54 算力总动员）→ 8（09-25 00:40）→ 10（09-25 11:3x，当时保守 +2，
因 bm-a 与并行会话共抢 4070S）→ **15（2026-11-17，CEO「极限满负荷」）**。

# 九、模型容量天花板（2026-11-18 实测，重要判断）

## 9.1 三次修复全部失效

CEO 当日要求「个性更强、各地的人都有」，做了三处改动，均未解决：

| 改动 | 预期 | 实测 |
|---|---|---|
| 分流闸 `wx-skip-weather`（2/3 席禁写天气） | 风降到 33% | 仍 **91.6%** |
| 注入稳定地域（8 区各 12-13%） | 各地口音 | 分布对了，生成时被模板淹没 |
| 骨架池 26 → **2825** 组合 | 开场不重复 | 组合生硬（「这会儿手里旧物搁到手边」），且**立刻被拒进禁令池** |

## 9.2 决定性证据：模型陷入强吸引子

同一批次里三条**独立生成**的条目，前 12 字完全相同：

> 「今天先记一句：袖口被风灌得鼓起来，我。」

换骨架后模型连新骨架一起污染：`citywide refusal-bans (12h) = 123`，最新一条正是刚下发的
组合骨架「这会儿手里秤盘理顺了些 @11:24:53」——**给什么骨架就抄什么骨架**。
实测 5 席连跑：**0 成功**（全部撞开场禁令），生产实际停滞。

## 9.3 判断：这不是 prompt 问题，是模型容量问题

1760 条/天 × 高质量 × 不重复，在 12 GB 卡上的 9B 模型**做不到**。可调空间已用尽：
人设/天气/反模板三条约束同时压，9B 只能保住一条。
**继续调 prompt 与闸门是负收益，必须改产量与质量的配比，或换模型。**

## 9.4 三条路（待 CEO 决策）

| 方案 | 产量 | 重复率 | 代价 |
|---|---|---|---|
| **A 保质量** | 约 300 条/天 | 低 | 慢，但每条经得起看 |
| B 保产量（当时现状） | 1700 条/天 | 风 92%、开场 57 人撞 | 快，但一眼机器味 |
| C 换模型 | — | 显著降低 | 27B 需 17 GB 显存，本机 12 GB 装不下 |

## 9.5 两条可复用的 prompt 工程教训

1. **给措辞示例 = 让模型逐字照抄**。prompt 里写「风不小/风挺大」当模板，结果全城都在刮这阵风。
   要它自己组织，只给事实（风速 15.9 m/s），不给说法。
2. **程序化组合能治重复，但会制造生硬**。「A×B×C」拼出的骨架像机器拼的，且一进禁令池就永久失效。
   要多样化，宁可人工写 200 条自然的，不要机器拼 2800 条。

## 9.6 另一处运维缺口

`ollama` 服务**整夜跑会挂**（次日 10:53 实测服务不可用，`warm-probe failed`，生产停摆一夜）。
`watchdog.py` 当时只查心跳/日志/泵产出，**没查 ollama 服务本身**——需补这一项。

# 十、形式分化：真正有效的解（2026-11-18）

## 10.1 CEO 的方法论纠正（重要）

原话：「**颗粒度不够细，还有就是你要去参考别人已有的模板啊什么的，GitHub 务必每次先去看一遍**」。

我当时已经改了四轮 prompt（分流闸/地域注入/骨架池/md5 散列），全在自己造。
**这是第二次违反「先搜 GitHub」铁律**（首次在 2026-10-16 已写进记忆）。
教训：改 prompt 之前先搜社区标准，比自己试错便宜一个数量级。

## 10.2 社区标准（GitHub 实测）

| 项目 | 星 | 对本题有用的东西 |
|---|---|---|
| **SillyTavern** | **35.7k** | Character Card V2 spec：角色一致性靠 **`mes_example`（示例对话）** 而非描述；`scenario` 给当前情境；`alternate_greetings` 给多条**完整开场**而非模板 |
| **DSH Tavern** | 1.6k | 「**前台模型只写正文，格式与校验交给后台**」——prompt 塞满禁令会分散注意力，这正是千篇一律的病根 |

**结论：给样文 > 给规则。** 我此前一直在写规则（"不要 A、不要 B"），社区的做法是给 2-3 条完整示例让它照着写。

## 10.3 8 种日记体（`Tools/ring_forms.py`）

按 cid 稳定分配，每种自带长度区间 + 2-3 条完整样文（few-shot）：

| 体式 | 字数 | 要点 |
|---|---|---|
| 抱怨 | 25-55 | 谁添了乱、哪口气咽不下 |
| 对话 | 40-75 | 用引号写，至少两句来回 |
| 记账 | 30-55 | 做了几单、进多少出多少，数字具体 |
| **看别人** | 40-70 | **全程不写自己，只写眼里那个人** |
| 就一句 | 10-25 | 只写一句，不要第二句 |
| 留话 | 30-50 | 给具体的人留话，称呼要具体 |
| 一件事 | 70-100 | 起因经过结果，可有意外 |
| 心气 | 25-50 | 别直接说情绪名，用手上动作带 |

## 10.4 实测效果（这是四轮 prompt 改动里唯一真正见效的）

改动前：全部 60-80 字第一人称独白、以「我」开头、以感悟收尾。
改动后（同一模型、同一批）：

- 字数**分化到 25-90 字**
- 出现真对话：「老李问这价能不能再低两分。我说不能…他咂咂嘴，掏出皱巴巴的一叠钞。」
- 出现具体数字：「修了三处缺口收五十六，换了两根铁丝，剩四十二块零头。」
- 出现具体人名：老张 / 王婶 / 阿婆 / 修鞋的老许

**「看别人」体式质量最高**——因为它天然禁止写"我"，逼着写具体的人与细节：

> 「对门那家老太太把刚晒过的被子收进楼道，说是怕鸟在上面拉。她家老头走了三年，两床旧被头还是叠得整整齐齐，像没变过模样。」
> 「巷口修鞋的老许手里夹着半截粉笔，头也没抬地给一只断了底的小靴描线，旁边蹲个小孩看了半个钟头。」

**How to apply**：想让人味强，把「必须写具体对象」写成体式约束，比写十条禁令有效。

## 10.5 两个技术坑

1. **PowerShell here-string 写中文 Python 代码会破坏引号**：`\"` 与 `` `n `` 在 here-string 里被展开，
   多次把 Python 文件写坏（`_form_blk = "` 未闭合）。改 Python 源码一律用编辑工具，不要用 shell 内联脚本。
2. **骨架按 cid 求和的散列会撞段**：`sum((i+1)*ord(ch))` 让相邻 cid 只差 1 → 落到相邻索引，
   而骨架池是「起手段×物件×收尾」连续排列 → 连续 cid 长期撞同一段起手（实测 8 条里 7 条都是「这会儿手里…」）。改 md5 后 40 个连续 cid 得到 40 种不同骨架。

## 10.6 新发现的漏拦

模型会**编造过的数据**：「**19 级的风**把屋顶老灯柱上的线扯得啪哒响」——实况 15.9 m/s ≈ 7 级。
这比用词问题严重（是事实错误），闸门需补「风力等级 / 数量级越界」检查。

# 十一、并发提速与评分器 v2（2026-11-18 下午）

## 11.1 诊断：瓶颈不在频次，在拒稿重试

CEO 问「GPU 使用频率能否继续拉高」。实测：

| 指标 | 实测 |
|---|---|
| GPU 平均利用率 | **34%**（30 个采样里 63% 是 ≤10%） |
| 每轮 | 8.5-9.5 分钟 / 16-20 批 |
| 每轮产出 | 34-56 条 |
| **成功率** | **13%**（34 条 ÷ 18 批 × 15 席） |

序列 `0 0 1 100 91 99 89 0 77 0 1 0 ...`：满负荷只有 4-6 秒，中间空 10-20 秒。
**87% 的算力烧在「写不合格 → 重试 → 再不合格 → 放弃」上。** 单纯把 10 分钟缩到 5 分钟只会更快地烧掉同样的拒绝。

## 11.2 并发方案：进程级，不是线程级

线程级并发有确凿的竞态风险：`sig` 是共享 dict，每席都要写 `sig["card_text"]/["cid"]/["pool_advice"]/["rumor"]/["goal"]`，
且接受后要写 `sig["batch_openings"]`——之前 `wx-skip-weather` 漏拦 6/9 就是共享 sig 被并发席交叉改写造成的。

**正法 = 进程级并发**：
1. `due_list.py` 先取全量 due，切成 N 段
2. N 个 `evolve --force <段> --no-commit --lock-name pN` 并发
3. 各进程独立 sig，天然无竞态
4. 主进程在 `--no-commit` 下统一 `git add/commit` 一次，避免抢 index.lock

新增参数：`--no-commit`（跳过提交）、`--lock-name`（自定义锁名）。

## 11.3 实测数字

| 配置 | 吞吐 | 成功率 | 显存余量 |
|---|---|---|---|
| 串行（基线） | 215-356 条/小时 | 13% | 充裕 |
| 并发 2 | **592 条/小时** | 89% | — |
| **并发 3（默认）** | **877 条/小时** | **89%** | 846 MiB |

单次 API 层验证：3 个请求串行 3.7s → 并行 1.7s，**加速 2.11x**。

**成功率暴涨的原因**：`--force <从 due_list 取的连续 id>` 选中的是**互不相同的人设**，
不像 `--batch N` 自动选人时常撞同街区/同模板；每批 12 席能写 11-12 条。

副作用：并发 3 显存只剩 846 MiB，驻留态门槛须从 900 降到 **500**，否则下一轮被自己的闸挡住。

## 11.4 评分器 v2：按造闸六问重做

旧评分器六问全没答（靶阈值、无负控、无边界、无验证记录）。新版：

**标定依据**（2714 条实测）：

| 指标 | p10 | p50 | p90 | max |
|---|---|---|---|---|
| 专名数 | 0 | **0** | 1 | 5 |
| 数字/量词 | 0 | **0** | 1 | 4 |
| 动词数 | 0 | **1** | 3 | 8 |
| 对白句数 | 0 | 0 | **0** | 4 |

阈值全部取自分位数（p50 = 及格线、p90 = 达标线），不再拍脑袋。

**负控暴露了致命缺陷**：5 条典型 AI 味在旧闸下拿 **44-55 分**——因为「长度合规/无天气/无编造」这些维度**不需要任何努力就满分**。
加**硬门槛**（必须「有动作 或 有对话」且「有人名 或 有数字 或 对话≥2」，否则总分封顶 **38**）后：
负控 38.0 < 40 PASS、正控 72.2 > 70 PASS → `SELFTEST PASS`。

**真实基线只有 49.2 分**（旧闸报 83.2 是虚高 34 分）。

## 11.5 AI 感的量化形态（本轮最重要的发现）

| 维度 | 2714 条实测 |
|---|---|
| 动词密度 | **36.3**（一条 64 字只有 2.7 个动词） |
| 专名 | **0.5**（平均半个人名） |
| 数字量词 | **1.7** |
| 少形容词 / 无空话 / 无编造 | 93-100（这些很容易达标） |

**结论：模型很会「不说错话」，但几乎不「说事情」。**
千篇一律的本质不是用词问题，是**没有人物、没有动作、没有数字，全是状态和形容**。
这也解释了为什么改 prompt 措辞四轮都没用——措辞改不了「没有事情发生」。
