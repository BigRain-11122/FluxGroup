# 养号线（B 站双号运营）2026-11-22 工程判据合订

> 只收仍然有效的判据与坑，过程叙事看 git log。基准数据另见 `bili-benchmarks.md`，
> 四环主人另见 `social-loop-conductor-20261120.md`。

## 一、CEO 定调（覆盖我此前的口径）

1. **可见率不是目标，回复质量才是**（原话「可见不重要」）。可见率只记录、不进判据、
   不做加量开关；判据换成"这条回复像不像真人、贴不贴题"。
2. **说话必须多元**（原话「参考他们的评论、高点赞数的评论，不要这么讲话」）：
   不是换同义词，是换**原型**——同一场景下不同人会有不同说话位置。
3. **我的话可选择性接受/科学改造后接受**：接到点状指令先出该领域的"面清单"再动手。

## 二、说话多元化的可复算做法

- `voice_spec.py`：从 6 万条真人评论按 **B 站自身分类**提炼 7 个原型，每原型配 8 条真实样本。
  原型必须来自平台分类，不是自己拍脑袋分的类。
- `voice_mine.py`：按点赞采高赞评论（955 → 2472 条），高赞样本单独成池供 few-shot。
- 提示词 = few-shot 样本 + **显式禁用词表**。实测：不加词表时 8 条候选有 5 条带"绝了"被闸拒；
  加了词表 0/8。**光给好样本不够，必须同时给禁词**，否则模型锁在最高频的那个词上。
- 弹幕：10 条模板 → 4 类 16 条 + 12 条人工筛通用句；锚点词改走领域词表，不用固定名词。

## 三、频率的真上限＝内容池，不是政策

- 池内 N 条 + 同视频 7 天 ≤1 条 ⇒ 每天 ≤ N/7。108 条 = 15 条/天，抬配额只会重复同一视频。
- 扩池 `pool_expand.py`（走 `archive/related`）：108 → 308 → 808 → 1208 → 1608 → 2008 条。
- **平台没有"一天只能评几条"的红线**，统计均值（20 天一条评论）不能当标准，
  那会把自己的活跃度压到不像活人。真实约束只有两个：能写出内容的新视频有多少、同视频重复窗口。
- `freq_policy.py` 五档 L1–L5（30–44 … 88–120 条/天），按实测升降；质量样本不足不升档。

## 四、四层"假阻塞"（22 小时不出稿的真实根因）

系统不是死了，是四道自家闸互相打架把活卡住：

1. **训练哨兵一刀切**：tick 见哨兵就整轮跳过，而训练脚本自己记着"训练 + 8788 + 采集同跑 10/10 成功"。
   → 正法：只走 8788 车道，不整轮让路。**就绪判据要按车道放行，不许一刀切。**
2. **GPU 租约 4h TTL**：出稿干等 90 秒放弃 → 改"受限共存"（8788 在位 + 间隔 ≥10 分钟），并跳过空等。
3. **领域闸把新视频全判死**：扩池后 2008 条没采过评论、topics 为空 → 加标题词兜底。
   **新增供给必须同步扩判据的兜底路径**，否则扩池等于扩死。
4. **发帖动作自身空等**：`post` 实测 59.99s = `goto` 60 秒超时后继续 → 改 15 秒超时即继续，
   实测降到 **3.0–3.6 秒**。**任何"操作很慢"先量单步耗时，别先怀疑模型或网络。**

## 五、必须记住的三条运维坑

1. **只增台账必须移出 git 跟踪**：机队每轮 `git pull --rebase --autostash`，把当晚 4 条真发记录整段冲掉，
   今日已发从 13 退回 9，配额与质量判据全失真。已 `git rm --cached`（`23a8bc2a6`），
   补录标 `recovered:true` 不伪装原文。**判据输入文件不许进同步面。**
2. **`KeepAlive` + `StartInterval` 同时写会狂重启**：实测智能体空转 174 次 → 去掉 KeepAlive；
   human 型任务取证一次即转 `waiting`，不许反复取证。
3. **改完即 commit + push**：未提交改动被机队 rebase 回滚四次（`DAEMON_HOLD_S`、goto 超时、
   `_log_op`、`pick` 函数、`sc/sp` 导入），中途 `NameError: pick` 让浏览分支整段不可用。

## 六、并行边界

- **可并行**：扩池（10 并发，808 源 6 分钟 → 1608 源 77 秒，8×）、补采（3 并发，60 视频 2.4 分钟
  → 40 视频 11 秒，13×）。各写各的文件 + 单实例锁。
- **不可并行**：训练与推理。同一块统一内存，硬并行就是换页，违反「不触发 swap 用满算力」判据。

## 七、常驻智能体的权限边界（写死，不许自己放宽）

- 允许：自建任务卡（Q-POOL/Q-HOT/Q-DIV 归它）、自验（事实没变不许标完成）、
  自愈（判据读错就改判据并重判）、交底（`ESCALATIONS.md` 一分钟可决）。
- 禁止：不发帖、不改阈值、不改代码。人判项（Q-DUP/Q-LEN/Q-AI/S8/S9）一律转 `waiting`。

## 八、质量判据七维（`reply_quality.py`）

具体性 / 人味 / 不撞模板 / 长度带 / 贴题 / 原型分布 / 人设漂移。
2026-11-22 实测 9 条：中位 80、具体 100%、贴题 100%、AI 腔 0%、撞模板 22%、长度带 67%。
两个短板当场修：撞开头改为**直接丢弃候选**（不打分）；字数带只留一处判据（命中 8/8）。
**弱信号**：回验时抓我方评论的点赞数，`arch_perf.py` 按原型汇总，样本 ≥5 后 20% 概率倾斜最优原型。

## 九、2026-11-22 夜：三方抢一个浏览器 + "在盘上≠在跑"

**总根因**：会话、采集、发帖共用同一个 `browser-profile`，而 `browserd` 是**单线程**服务端。
任何动作排进它都要占唯一线程，于是发帖被压在浏览/采评论后面：实测 post 77–98 秒，
而浏览器里真正发帖只三五秒。`gen` 只有 10–14 秒——**慢的从来不是模型**。

1. **让路判据要覆盖所有可推迟动作**，只拦 `browse` 不够：`hot`（采评论）/`roots`（楼中楼）
   同样是重活。标记期内除 `post` 自己外一律让路。
2. **发帖方不许自我让路**：`POST-PENDING` 是自己写的，判据里必须用 `yield_ok` 区分，
   否则第一条必然"自己被自己挡住"而失败。
3. **采集让路要记 DEFER，不能记 FAIL**：DEFER 不进 24 小时退避、退出码为 0；
   判成 FAIL 会把语料供给永久压死。
4. **计时必须拆两段**：`post_s`＝拿到浏览器后到发完；`post_queue_s`＝排队时间。
   混在一起只会让人去优化错误的环节。
5. **"配置在盘上"不等于"作业在跑"**：`com.fluxgroup.practicetick` 的 plist 一直在
   `~/Library/LaunchAgents/`，但 launchd 里根本没有它 —— 今晚 4 条是手动跑的。
   判"常驻在跑"只能查 `launchctl list`，不能查 plist 是否存在。
6. **`launchctl submit` + keepalive 会狂重启**：`corpusbake` 累计 runs=18441，
   日志永远只有两行（本来就没活）。正法＝落成 plist，`StartInterval` 1800、`KeepAlive` false。
7. **智能体 human 卡转 waiting 必须带到期**（`WAIT_REARM=2h`），并"理由串一变就重开卡"。
   原来 `pick_item` 改了状态但空闲分支不落盘 → 每次进程读回 open，attempts 一路涨到 175。
